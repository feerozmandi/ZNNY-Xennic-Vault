# PRJ-IEE-003 — معماری سامانه و Field API

> [!abstract] هدف
> تعریف معماری نهایی سامانه: یک پایگاه‌داده دائمی PostgreSQL به‌عنوان منبع یگانه حقیقت، یک **Field API** به‌عنوان تنها مسیر خواندن و نوشتن داده، و دو رابط کاربری (ربات بله و پنل WordPress) که هر دو فقط کلاینت این API هستند — همراه با مرزهای دقیق، قرارداد رابط‌ها و پشته فناوری.

## ۱. هدف (Why)

مأموریت، چهار جزء را نام برده است: ربات بله، پنل WordPress، Field API و PostgreSQL. خطر اصلی در چنین طرحی، **تکرار منطق کسب‌وکار در چند جا** است: ربات یک قاعده اعتبارسنجی داشته باشد، WordPress قاعده دیگری، و n8n قاعده سوم. نتیجه، داده ناسازگار در پایگاه‌داده‌ای است که قرار است سال‌ها مرجع باشد.

این نود یک قاعده ساده و سخت تعیین می‌کند:

> [!important] قاعده واحد
> **هیچ رابط کاربری، منطق کسب‌وکار ندارد.** هر دو رابط فقط: (۱) ورودی را جمع می‌کنند، (۲) به Field API می‌فرستند، (۳) پاسخ را نمایش می‌دهند. اعتبارسنجی، کنترل تعارض، سطح دسترسی، محاسبه اولویت و ثبت تاریخچه **فقط** در Field API انجام می‌شود.

دلیل این انتخاب، هم‌راستایی مستقیم با [[META-INT-080 — معماری کلان سیستم‌عامل هوشمند سازمانی Xennic|META-INT-080]] (بند ۲.۳، اصل API-first و Single Source of Truth) و آمادگی برای اتصال آینده به پلتفرم Xennic است: هر ماژول آینده (CRM، تأمین، پلتفرم) می‌تواند همان API را مصرف کند، بدون آنکه بداند امروز ربات بله وجود داشته است.

### ۳.۲. اجزا و مسئولیت

| جزء | محل اجرا | مسئولیت | مسئولیت ندارد |
|---|---|---|---|
| ربات بله | درون Field API (ماژول `bale_gateway`) | دریافت پیام، اجرای جریان گفت‌وگو، فراخوانی سرویس‌های دامنه | ذخیره مستقیم در پایگاه‌داده، تحلیل پیچیده |
| Field API | VPS (Docker) | منطق کسب‌وکار، اعتبارسنجی، دسترسی، تعارض، تاریخچه، API عمومی | رابط گرافیکی، پردازش سنگین صوت |
| پنل WordPress | هاست اشتراکی cPanel | نمایش، ویرایش محدود، گزارش و خروجی Excel | اتصال مستقیم به PostgreSQL، منطق دامنه |
| PostgreSQL | VPS (Docker، بدون پورت عمومی) | منبع یگانه حقیقت، محدودیت‌های یکتایی، تاریخچه، جست‌وجو | — |
| n8n | VPS (Docker) | کارهای غیرهمگام: رونویسی صوت، پشتیبان، یادآوری، گزارش | منطق تعاملی ربات، اعتبارسنجی ورودی |
| Storage | VPS (فایل‌سیستم محافظت‌شده) | نگهداری عکس، صوت، کاتالوگ | سرو عمومی مستقیم فایل |
| Caddy | VPS | TLS، Reverse Proxy، محدودیت نرخ، هدرهای امنیتی | منطق دسترسی سطح رکورد |

### ۳.۳. چرا ربات، ماژول داخل Field API است و نه یک Workflow در n8n؟

| معیار | ربات در n8n | **ربات در Field API (انتخاب‌شده)** |
|---|---|---|
| سرعت توسعه در ۶ روز | گراف پیچیده و سخت‌آزمون | کد پایتون آزمون‌پذیر |
| منطق وضعیت گفت‌وگو (State) | نگهداری State در n8n شکننده | جدول State در پایگاه‌داده |
| اعتبارسنجی و کنترل تعارض | تکرار منطق | همان لایه دامنه |
| آزمون خودکار | دشوار | pytest |
| استقرار | یک سرویس اضافه | همان سرویس موجود |

> [!note] نقش n8n باقی می‌ماند
> n8n برای کارهای **غیرتعاملی** (رونویسی صوت، پشتیبان شبانه، یادآوری روزانه، تولید گزارش) بهترین ابزار است و همان‌جا می‌ماند؛ فقط چرخه گفت‌وگو با کاربر در آن پیاده نمی‌شود. ثبت Workflowها طبق [[META-INT-090 — رجیستری Workflowهای n8n|META-INT-090]] الزامی است (نود ۰۰۸).

## ۴. مرز WordPress و Payload CMS

[[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]] برای **وب‌سایت عمومی** CMS را Payload تعیین کرده است. مأموریت فعلی برای **پنل مدیریتی داخلی** WordPress روی هاست اشتراکی را الزام کرده است. این دو در تعارض نیستند، به شرط مرزبندی صریح:

| موضوع | وب‌سایت عمومی | پنل این پروژه |
|---|---|---|
| ابزار | Next.js + Payload (تصمیم `META-INT-150`) | WordPress روی cPanel (الزام مأموریت) |
| دامنه | `xennic.ir` و زیردامنه‌های عمومی | زیردامنه داخلی/محافظت‌شده |
| منبع داده | PostgreSQL نمونه پلتفرم | همان نمونه، از طریق Field API |
| دسترسی به پایگاه‌داده | از طریق لایه اپلیکیشن خودش | **هیچ** — فقط HTTPS به Field API |
| محتوا | محتوای بازاریابی و عمومی | داده عملیاتی شرکت‌ها، مذاکرات، وظایف |
| کاربران | بازدیدکننده عمومی + `Staff` | کاربران داخلی محدود (۲ تا ۴ نفر) |

> [!important] تصمیم D-2 و پیامد آن
> WordPress **هیچ جدولی** برای شرکت‌ها، مخاطبان، محصولات یا مذاکرات در MySQL نمی‌سازد؛ فقط تنظیمات پلاگین و لاگ خروجی‌ها. اگر روزی WordPress حذف شود، داده‌ها دست‌نخورده در PostgreSQL می‌مانند — این تعریف عملی «عدم اتصال مستقیم WordPress به PostgreSQL» در مأموریت است.

## ۵. مرزهای اعتماد (Trust Boundaries)

| مرز | از | به | کنترل |
|---|---|---|---|
| TB-1 | گوشی → Bale API | اینترنت عمومی | توکن ربات؛ هویت کاربر با `chat_id` |
| TB-2 | Bale API → Field API | اینترنت عمومی | امضای مخفی مسیر Webhook یا IP/Secret؛ در حالت Polling، درخواست خروجی |
| TB-3 | WordPress (cPanel) → Field API | اینترنت عمومی | توکن سرویس + محدودیت دامنه مبدأ (CORS) + محدودیت نرخ |
| TB-4 | Field API → PostgreSQL | شبکه داخلی Docker | کاربر دیتابیس محدود، بدون Superuser، بدون پورت عمومی |
| TB-5 | n8n → Field API | شبکه داخلی/VPS | توکن سرویس مستقل با حداقل مجوز |
| TB-6 | کاربر → WordPress Admin | HTTPS | ورود WordPress + محدودیت IP (اختیاری) + نقش‌ها |

> [!warning] قاعده طلایی
> توکن سرویس WordPress هرگز در مرورگر کاربر ظاهر نمی‌شود؛ همه فراخوانی‌ها سمت سرور PHP انجام می‌شود. توکن ربات بله هرگز در لاگ نوشته نمی‌شود ([[META-INT-100 — مدیریت Secrets و Credentials|META-INT-100]]).

## ۸. قرارداد Field API

نسخه پایه: `https://<host>/api/v1`. همه پاسخ‌ها JSON؛ زمان‌ها ISO-8601 با منطقه زمانی؛ شناسه‌ها UUIDv7 (قابل مرتب‌سازی زمانی).

| منبع | مسیرها | توضیح |
|---|---|---|
| `organizations` | `GET/POST /organizations`، `GET/PATCH /organizations/{id}` | شرکت/سازنده/تأمین‌کننده |
| `contacts` | `GET/POST /contacts`، `PATCH /contacts/{id}` | مخاطب با نقش و روش تماس |
| `products` | `GET/POST /products` | محصول/دسته با مشخصات کلیدی |
| `interactions` | `GET/POST /interactions` | مذاکره، تماس، بازدید (فقط افزودنی) |
| `claims` | `POST /claims`، `GET /claims?subject=` | ادعای دارای منبع و سطح اعتبار |
| `sources` | `GET/POST /sources` | منبع: کاتالوگ، سایت، کارت ویزیت، شاهد انسانی |
| `opportunities` | `GET/POST/PATCH /opportunities` | فرصت همکاری با مرحله و ارزش |
| `tasks` | `GET/POST/PATCH /tasks`، `POST /tasks/{id}/complete` | وظیفه و پیگیری |
| `visits` | `POST /visits`، `GET /visits?exhibition=` | بازدید غرفه |
| `booths` | `GET /booths?hall=&q=` | غرفه و موقعیت |
| `files` | `POST /files`، `GET /files/{id}/url` | آپلود و URL امضاشده |
| `search` | `GET /search?q=` | جست‌وجوی یکپارچه |
| `brief` | `GET /brief/{organization_id}` | برگه پیش‌بازدید |
| `exports` | `GET /exports/companies.csv`، `GET /exports/export.xlsx` | خروجی گزارش |
| `meta` | `GET /meta/enums`، `GET /healthz` | فهرست مقادیر مجاز، سلامت |

> اگر سامانه شرکت مشابه تشخیص داد، درخواست را رد نمی‌کند؛ `201` با فهرست هشدار برمی‌گرداند و به کاربر اجازه می‌دهد ادغام یا ادامه را انتخاب کند. در محیط نمایشگاه، مسدودسازی معادل از دست رفتن اطلاعات است.

## ۹. مدل خطا، نسخه‌بندی و Idempotency

### ۹.۱. مدل خطای یکسان

```json
{
  "error": {
    "code": "conflict_version_mismatch",
    "message": "رکورد توسط کاربر دیگری تغییر کرده است.",
    "field_errors": [{"field": "phone", "reason": "invalid_format"}],
    "current_version": 7,
    "your_version": 6
  }
}
```

| کد HTTP | کد خطا | معنی و رفتار رابط |
|---|---|---|
| 400 | `validation_error` | ورودی نامعتبر؛ نمایش پیام فیلد |
| 401 | `unauthenticated` | توکن نامعتبر/منقضی |
| 403 | `forbidden` | نقش اجازه ندارد |
| 404 | `not_found` | رکورد حذف/ناموجود |
| 409 | `conflict_version_mismatch` | تعارض ویرایش؛ نمایش تفاضل |
| 409 | `duplicate_client_uuid` | تکرار ارسال؛ پاسخ همان رکورد قبلی |
| 422 | `business_rule_violation` | مثلاً ادعای `verified` بدون منبع |
| 429 | `rate_limited` | تلاش مجدد با فاصله |
| 503 | `dependency_unavailable` | خطای پایگاه‌داده/سرویس جانبی |

### ۹.۲. نسخه‌بندی و Idempotency

| موضوع | قاعده |
|---|---|
| نسخه API | پیشوند مسیر `/api/v1`؛ تغییر شکننده = `/api/v2`؛ افزودن فیلد اختیاری، شکننده نیست |
| تعارض | هر `PATCH` باید `If-Match: <version>` بفرستد؛ نبود آن در رکوردهای مهم رد می‌شود |
| تکرار ارسال | `Idempotency-Key` اجباری برای `POST`؛ نگهداری ۴۸ ساعت |
| تکرار رکورد | `client_uuid` یکتا در سطح پایگاه‌داده (تولیدشده روی گوشی) |
| زمان | ذخیره UTC؛ نمایش بر اساس منطقه زمانی تهران |

## ۱۰. جریان‌های کلیدی

### ۱۰.۱. ثبت مذاکره از ربات

```text
پیام کاربر → bale_gateway (تشخیص intent)
   → domain service: interactions.create()
   → اعتبارسنجی (طرف مقابل، موضوع، اقدام بعدی)
   → درج در PostgreSQL + audit_event
   → پاسخ تأیید کوتاه با شناسه و لینک برگه شرکت
```

### ۱۰.۲. خواندن و ویرایش از WordPress

```text
مدیر در پنل → فرم PHP → wp_remote_request(POST/PATCH) → Field API
   → بررسی توکن و نقش (wp_service)
   → اعتبارسنجی + کنترل تعارض
   → پاسخ JSON → رندر سمت سرور + کش کوتاه (۶۰ ثانیه)
```

### ۱۰.۳. آپلود عکس/صوت

```text
فایل از بله → getFile → دانلود به حافظه موقت
   → بررسی نوع واقعی (magic bytes) و اندازه
   → محاسبه sha256 → ذخیره در Storage با نام UUID
   → درج متادیتا در crm.attachments
   → اتصال به شرکت/تعامل
   → (اختیاری) صف رونویسی در n8n  ← نود ۰۰۸
```

### ۱۰.۴. خروجی هوش مصنوعی

```text
متن/صوت → سرویس محلی → نتیجه
   → درج در crm.ai_suggestions با status=proposed
   → نمایش در پنل به‌عنوان «پیشنهاد»
   → تأیید یا رد انسانی → تولید claim با منبع مشخص
```

> [!warning] ممنوعیت صریح
> هیچ مسیری وجود ندارد که خروجی AI مستقیماً ستون قطعی یک شرکت را تغییر دهد. این محدودیت در لایه دامنه اعمال می‌شود، نه با آموزش کاربر.

## ۱۱. پشته فناوری و استقرار

| لایه | انتخاب | دلیل |
|---|---|---|
| زبان و فریم‌ورک | Python 3.12 + FastAPI | همان پشته مصوب پلتفرم در [[L2-PLT-001 — Xennic v1\|L2-PLT-001]]؛ آزمون‌پذیری و OpenAPI خودکار |

| اعتبارسنجی | Pydantic v2 | پیام خطای ساخت‌یافته |
| پایگاه‌داده | PostgreSQL 16 | مصوب `META-INT-150`؛ JSONB، ایندکس فارسی، محدودیت یکتایی |
| وب‌سرور/Proxy | Caddy | TLS خودکار، سبک، پیکربندی کوتاه |
| کانتینر | Docker + Compose | هم‌راستا با پشته فعلی VPS |
| آزمون | pytest + httpx | آزمون قرارداد و تعارض |
| لاگ و پایش | لاگ JSON + Dozzle/Uptime | سبک و متناسب با ۶ گیگابایت RAM |
