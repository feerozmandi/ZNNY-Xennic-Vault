## ۱. هدف (Why)

سه ماه پس از نمایشگاه، دو سناریو ممکن است: (۱) داده‌ای تمیز، قابل جست‌وجو و متصل به CRM داریم که مبنای مذاکره و تأمین است؛ (۲) یک فایل Excel نیمه‌کاره و چند عکس پراکنده در گوشی. تفاوت این دو، در لحظه نمایشگاه تعیین نمی‌شود؛ در **بهره‌برداری و تحویل** تعیین می‌شود.

این نود سه خلأ رایج را پر می‌کند:

| خلأ | پیامد | پاسخ این نود |
|---|---|---|
| نداشتن رویه پشتیبان و بازیابی آزمون‌شده | از دست رفتن کل داده در یک خطا | بندهای ۴ و ۵ |
| نبود برنامه تحویل و ادغام | داده در پایگاه‌داده می‌ماند و استفاده نمی‌شود | بندهای ۷ و ۸ |
| نداشتن نقشه توسعه | هر نمایشگاه، بازنویسی از صفر | بند ۹ |

## ۴. سیاست پشتیبان‌گیری

| مورد | محتوا | فرکانس | محل | نگهداشت |
|---|---|---|---|---|
| پایگاه‌داده (`crm` + `iee1405`) | `pg_dump` فشرده | روزانه ۲۳:۳۰ | VPS + کپی خارج از سرور | ۳۰ روز روزانه، ۱۲ ماه ماهانه |
| فایل رسانه | آرشیو `uploads/` | هفتگی (و روزانه فقط فایل‌های جدید) | VPS + کپی خارج | ۹۰ روز |
| پیکربندی | `docker-compose.yml`، Caddyfile، `.env.example` | هر تغییر | مخزن `xennic-infra-backups` | دائمی |
| رازها | `.env` واقعی | هر تغییر | فقط Password Manager مالک | دائمی |
| خروجی گزارش | Excel/CSV روزانه | روزانه | کپی گزارش‌ها | ۶ ماه |

### ۴.۱. قواعد اجرایی

```bash
# نمونه پشتیبان پایگاه‌داده (روی سرور، در مسیر پشته)
STAMP=$(date +%F-%H%M)
docker exec xennic-postgres pg_dump -U field_api -d xennic_core -Fc \
  > /srv/xennic-field/backups/db/xennic_core-$STAMP.dump

# فشرده‌سازی و رمزنگاری (age؛ کلید عمومی در سرور، کلید خصوصی در Password Manager)
age -r "$AGE_RECIPIENT" -o /srv/xennic-field/backups/db/xennic_core-$STAMP.dump.age \
  /srv/xennic-field/backups/db/xennic_core-$STAMP.dump
sha256sum /srv/xennic-field/backups/db/xennic_core-$STAMP.dump.age \
  > /srv/xennic-field/backups/db/xennic_core-$STAMP.dump.age.sha256
rm /srv/xennic-field/backups/db/xennic_core-$STAMP.dump   # نسخه رمزنگاری‌نشده حذف شود
```

| # | قاعده |
|---|---|
| ۱ | پشتیبان **رمزنگاری‌شده** ذخیره می‌شود؛ نسخه رمزنگاری‌نشده باقی نمی‌ماند |
| ۲ | هر پشتیبان، فایل `sha256` جداگانه دارد |
| ۳ | حداقل یک نسخه خارج از VPS (لپ‌تاپ مالک یا مخزن خصوصی) نگهداری می‌شود — قاعده ۳-۲-۱ |
| ۴ | نتیجه هر پشتیبان (موفق/ناموفق + حجم + مدت) در بله اعلام می‌شود |
| ۵ | پشتیبان بدون آزمون بازیابی، معتبر نیست |
| ۶ | پشتیبان هرگز در Vault عمومی، چت یا ایمیل معمولی ارسال نمی‌شود |

## ۵. آزمون بازیابی (Runbook)

### ۵.۱. آزمون پیش از نمایشگاه (اجباری)

| گام | کار | معیار |
|---|---|---|
| ۱ | ساخت پایگاه‌داده آزمایشی جدا (`xennic_core_restore_test`) | موفق |
| ۲ | بازیابی آخرین پشتیبان روی آن | بدون خطا |
| ۳ | شمارش ردیف‌های جداول اصلی و مقایسه با اصلی | اختلاف ۰ |
| ۴ | بازیابی سه فایل نمونه از آرشیو رسانه و بررسی هش | تطبیق SHA-256 |
| ۵ | اجرای Field API روی پایگاه‌داده بازیابی‌شده و آزمون `healthz` + یک جست‌وجو | موفق |
| ۶ | حذف پایگاه‌داده آزمایشی و ثبت نتیجه در گزارش | انجام‌شده |

```bash
# نمونه بازیابی (محیط آزمایشی — هرگز روی پایگاه‌داده واقعی)
createdb -h 127.0.0.1 -U postgres xennic_core_restore_test
age -d -i ~/age-key.txt -o /tmp/restore.dump /srv/xennic-field/backups/db/<file>.dump.age
pg_restore -h 127.0.0.1 -U postgres -d xennic_core_restore_test --no-owner /tmp/restore.dump
psql -h 127.0.0.1 -U postgres -d xennic_core_restore_test \
  -c "SELECT 'organizations', count(*) FROM crm.organizations UNION ALL
      SELECT 'interactions', count(*) FROM crm.interactions UNION ALL
      SELECT 'claims', count(*) FROM crm.claims;"
```

> [!important] زمان هدف بازیابی
> هدف: بازیابی کامل در **کمتر از ۳۰ دقیقه** با Runbook. اگر بیش از این طول کشید، Runbook ناقص است یا پشتیبان سالم نیست — هر دو باید پیش از نمایشگاه اصلاح شوند.

### ۵.۲. بازیابی اضطراری حین نمایشگاه

| وضعیت | تصمیم | اقدام |
|---|---|---|
| از دست رفتن چند رکورد (خطای کاربر) | ادامه کار | بازیابی همان رکورد از `deleted_at`/Audit Log |
| خرابی پایگاه‌داده | توقف نوشتن | اعلام به مالک، ادامه ثبت روی برگه، بازیابی پس از پایان روز |
| خرابی کامل سرور | توقف سامانه | انتقال به برگه کاغذی؛ بازیابی در اولین فرصت |

## ۸. مسیر CRM و سامانه تأمین

### ۸.۱. نگاشت موجودیت‌ها

| این پروژه | مقصد در `L2-OPS-002` | نکته |
|---|---|---|
| `crm.organizations` | `Supplier` / `Customer` / `Manufacturer` | نقش با `org_type` تعیین می‌شود؛ یک شرکت می‌تواند هر دو باشد |
| `crm.contacts` | `SupplierContact` / `CustomerContact` | انتقال با حفظ نقش |
| `crm.products` | `Product` + `ProductSpecification` | نیازمند بازبینی فنی پیش از ورود به کاتالوگ رسمی |
| `crm.claims` | `CatalogDocument` / فیلدهای مشخصات | فقط ادعاهای `verified`/`observed` مستقیم منتقل می‌شوند |
| `crm.interactions` | `Activity` | تاریخچه مذاکره |
| `crm.opportunities` | `RFQ` (در صورت خرید) یا فرصت فروش | نگاشت با تصمیم انسانی |
| `crm.tasks` | وظایف پیگیری | انتقال کامل |

> [!warning] قاعده «ورود کنترل‌شده به کاتالوگ»
> ادعای `reported` هرگز مستقیم به کاتالوگ رسمی محصول منتقل نمی‌شود؛ طبق `L2-OPS-002` بند ۶، کاتالوگ مرجع قیمت و موجودی است و ورود داده تأییدنشده به آن، اعتبار سامانه را از بین می‌برد.

### ۸.۲. روش انتقال

| گام | روش |
|---|---|
| ۱ | خروجی استاندارد از نمای `crm.v_export_companies` (CSV/Excel) |
| ۲ | بازبینی و تأیید انسانی هر گروه |
| ۳ | ورود از طریق API مقصد (اگر موجود) یا Import کنترل‌شده با گزارش خطا |
| ۴ | ثبت «شناسه منبع» در مقصد (`source_system='iee1405'`, `source_id`) |
| ۵ | تطبیق شمارش ردیف‌ها و تأیید نهایی |

> [!note] چرا انتقال خودکار دوطرفه ممنوع است؟
> همگام‌سازی دوطرفه بدون مالکیت داده، به تعارض و تکرار منجر می‌شود. انتقال **یک‌طرفه و یک‌بار** است؛ پس از آن، مرجع شرکت‌ها در CRM است و این سامانه فقط سابقه نمایشگاه را نگه می‌دارد (طبق همان اصل Single Source of Truth).

## ۹. نمایشگاه بعدی و توسعه

| # | قابلیت | مسیر توسعه |
|---|---|---|
| ۱ | نمایشگاه بعدی (`IEE1406`) | افزودن یک ردیف در `iee1405.exhibitions` یا Schema جدید — بدون تغییر CRM |
| ۲ | ورود داده از رویدادهای دیگر (نمایشگاه، کنفرانس، سفر تجاری) | همان `crm.*`؛ فقط `exhibition_id` یا `event_id` تغییر می‌کند |
| ۳ | اپلیکیشن موبایل سبک | در صورت تأیید نیاز واقعی پس از نمایشگاه |
| ۴ | استخراج خودکار از کاتالوگ (OCR + AI) | پیشنهاد، نه تصویب؛ مسیر `ai_suggestions` |
| ۵ | دستیار پرسش‌وپاسخ روی داده نمایشگاه | ایندکس Qdrant از ادعاهای تأییدشده |
| ۶ | ادغام با پلتفرم Xennic | مصرف همان Field API، بدون تغییر دادگان |

> [!tip] اصل «هر نمایشگاه، یک ردیف»
> اگر برای نمایشگاه بعدی نیاز به بازنویسی Schema باشد، طراحی فعلی اشتباه بوده است. آزمون صحت این ادعا: افزودن نمایشگاه ۱۴۰۶ نباید بیش از یک Migration کوچک هزینه داشته باشد.
