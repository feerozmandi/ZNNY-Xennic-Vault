## ۱. هدف (Why)

مرحله اول مأموریت، «ممیزی واقعی VPS و PostgreSQL موجود» است. بدون این ممیزی، هر تصمیمی درباره محل اجرای Field API، ساخت Schema جدید یا ظرفیت سرور، حدس است — و تجربه پیشین شرکت (درس [[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]] بند ۸) نشان می‌دهد تصمیم‌های مبتنی بر فرض، گران تمام می‌شوند.

این نود سه کار می‌کند:

1. آنچه **از قبل مستند و تأییدشده** است را از [[META-INT-140 — نقشه مهاجرت زیرساخت اتوماسیون به سرور اختصاصی (VPS)|META-INT-140]] جمع می‌کند (تا ممیزی از صفر شروع نشود).
2. یک چک‌لیست **فقط‌خواندنی** و قابل اجرا تعیین می‌کند که در یک نشست SSH، وضعیت واقعی را ثبت می‌کند.
3. تصمیم‌های استقرار و بزرگ‌ترین ریسک (دسترسی عمومی امن) را با گزینه‌های مشخص، باز می‌کند.

## ۲. پاسخ پرسش «روش اتصال»

مأموریت (بند ۹) پرسیده است: «اتصال فعلی کاربر به VPS چگونه انجام می‌شود؟ ترمینال Linux و SSH، PuTTY، پنل ارائه‌دهنده، یا هنوز SSH راه‌اندازی نشده است؟»

> [!important] پاسخ مستند
> بر اساس شواهد ثبت‌شده در [[META-INT-140 — نقشه مهاجرت زیرساخت اتوماسیون به سرور اختصاصی (VPS)|META-INT-140]] (به‌روزرسانی‌های ۱۴۰۵-۰۸-۰۳ تا ۱۴۰۵-۰۸-۰۴)، **SSH راه‌اندازی شده و کار می‌کند**: ورود با کلید ed25519 برای کاربر غیر-روت `xennic` با `sudo`، ورود روت و ورود با رمز غیرفعال، و پشته Docker مستقر شده است. بنابراین پرسش «آیا SSH راه‌اندازی شده؟» **منتفی** است.
>
> پرسش باقی‌مانده فقط این است: **از کدام ابزار محلی استفاده می‌کنید؟** سه مسیر ممکن است و هر سه در ادامه آمده‌اند.

### ۲.۱. گزینه الف — ترمینال لینوکس/macOS یا WSL در ویندوز

```bash
# پیش‌نیاز: کلید خصوصی در ~/.ssh/ و پیکربندی میزبان در ~/.ssh/config
# (پورت، میزبان و نام کاربر در META-INT-140 ثبت شده است)
ssh xennic-vps
```

نمونه پیکربندی `~/.ssh/config` (مقادیر از سند زیرساخت):

```text
Host xennic-vps
    HostName <IP یا نام میزبان ثبت‌شده در META-INT-140>
    Port <پورت واقعی SSH ثبت‌شده در META-INT-140>
    User xennic
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30
```

### ۲.۲. گزینه ب — PuTTY در ویندوز

| گام | کار |
|---|---|
| ۱ | ساخت کلید در PuTTYgen یا استفاده از کلید موجود (فرمت `.ppk`) |
| ۲ | `Connection → SSH → Auth → Credentials` → انتخاب فایل `.ppk` |
| ۳ | `Session`: Host Name و Port (طبق سند زیرساخت) و Connection type: SSH |
| ۴ | ذخیره Session با نام `xennic-vps` |
| ۵ | ورود با کاربر `xennic` (نه `root`) |

### ۲.۳. گزینه ج — پنل ارائه‌دهنده (رادکام)

پنل فقط برای موارد زیر لازم است، نه برای ممیزی فنی:

- ری‌استارت اضطراری سرور
- مشاهده وضعیت پنل، مصرف منابع و بازه سرویس
- تیکت پشتیبانی (مثلاً مشکل شبکه/پورت)

> [!warning] قاعده
> ممیزی **نباید** از طریق کنسول پنل انجام شود مگر SSH از دسترس خارج شده باشد؛ کنسول پنل معمولاً امکانات کپی/لاگ محدود دارد و خطای تایپی در آن گران است.

### ۲.۴. اگر کلید در دسترس نیست

| وضعیت | اقدام |
|---|---|
| کلید خصوصی گم شده | ساخت کلید جدید در پنل یا از طریق کنسول، افزودن به `~/.ssh/authorized_keys` کاربر `xennic`، ثبت در Password Manager |
| پورت یا IP تغییر کرده | بررسی پنل ارائه‌دهنده و تیکت؛ ثبت نتیجه در `META-INT-140` |
| سرور ری‌استارت شده و سرویس‌ها بالا نیامده‌اند | `docker compose up -d` در مسیر پشته (`~/xennic-infra/`)، سپس ممیزی |

## ۴. قاعده «فقط خواندن»

> [!warning] این ممیزی هیچ تغییری اعمال نمی‌کند
> در گام ممیزی، هیچ بسته‌ای نصب، هیچ سرویسی متوقف، هیچ فایلی حذف و هیچ پورتی باز نمی‌شود. تمام دستورات بند ۵ **خواندنی** هستند. تغییرات، پس از تأیید مالک و در یک گام جداگانه (با ثبت در تاریخچه) انجام می‌شود.

سه استثنای ظاهری (که تغییری در سیستم نیستند):

- `docker stats --no-stream` (فقط یک نمونه می‌گیرد)
- `du`/`df` (خواندن)
- `psql -c "SELECT …"` (فقط پرس‌وجو)

## ۵. چک‌لیست ممیزی سیستم

```bash
# ══════════ ۱) هویت و سیستم ══════════
date; timedatectl | head -3
lsb_release -a; uname -r
whoami; id
nproc; free -h; df -h /; df -i /

# ══════════ ۲) SSH و دسترسی ══════════
sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|pubkeyauthentication|port'
sudo last -n 10
ss -tlnp | sed -n '1,40p'

# ══════════ ۳) آتش‌دیوار ══════════
sudo ufw status verbose

# ══════════ ۴) Docker و سرویس‌ها ══════════
docker version --format '{{.Server.Version}}'
docker compose version
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker stats --no-stream
docker network ls

# ══════════ ۵) فایل‌سیستم و مصرف ══════════
sudo du -sh /var/lib/docker 2>/dev/null
sudo du -sh /home/xennic/* 2>/dev/null | sort -h | tail -10
df -h

# ══════════ ۶) رمزنگاری/دامنه ══════════
sudo ss -tlnp | grep -E ':80|:443' || echo "هیچ سرویس روی 80/443 گوش نمی‌دهد"
dig +short A xennic.ir 2>/dev/null || nslookup xennic.ir
```

### ۵.۱. تفسیر نتایج

| یافته | معنی | اقدام |
|---|---|---|
| `PermitRootLogin yes` | ریسک امنیتی | ثبت در گزارش؛ رفع در گام سخت‌سازی (جدا) |
| `PasswordAuthentication yes` | ریسک امنیتی | ثبت؛ رفع در گام سخت‌سازی |
| پورت `5432` روی `0.0.0.0` | ریسک بحرانی | توقف فوری سرویس و رفع پیکربندی |
| `docker stats` بالای ۸۰٪ RAM | ظرفیت ناکافی | حذف/توقف سرویس غیرضروری، ارتقای پلن |
| `/` بالای ۸۰٪ | ریسک پرشدن دیسک | آرشیو/پاک‌سازی فایل‌های قدیمی |
| هیچ سرویس روی ۹۰:۸۰ | آماده برای Caddy | ادامه به بند ۸ |

## ۶. ممیزی PostgreSQL

### ۶.۱. شناسایی نمونه‌های موجود

```bash
# کدام کانتینر PostgreSQL در حال اجراست؟
docker ps --format '{{.Names}}\t{{.Image}}' | grep -i postgres

# نسخه و مسیر داده
docker exec <pg-container> postgres --version
docker exec <pg-container> sh -lc 'echo $PGDATA'

# فهرست پایگاه‌داده‌ها و اندازه‌ها
docker exec -e PGPASSWORD="$PGPASS" <pg-container> \
  psql -U <user> -d postgres -c "\l+"

# کاربران و مجوزها
docker exec -e PGPASSWORD="$PGPASS" <pg-container> \
  psql -U <user> -d postgres -c "\du"

# افزونه‌های نصب‌شده
docker exec -e PGPASSWORD="$PGPASS" <pg-container> \
  psql -U <user> -d <db> -c "SELECT name, default_version, installed_version FROM pg_available_extensions WHERE installed_version IS NOT NULL;"

# پیکربندی اتصال
docker exec -e PGPASSWORD="$PGPASS" <pg-container> \
  psql -U <user> -d postgres -c "SHOW listen_addresses;" -c "SHOW ssl;" -c "SHOW max_connections;"
```

### ۶.۲. آنچه باید در گزارش ممیزی ثبت شود

| # | مورد | مقدار |
|---|---|---|
| ۱ | تعداد نمونه‌های PostgreSQL | |
| ۲ | نسخه دقیق | |
| ۳ | حجم دیتابیس‌های موجود | |
| ۴ | کاربران و نقش‌ها | نام نقش + مجوز (بدون رمز) |
| ۵ | افزونه‌های نصب‌شده (`pg_trgm`, `pgcrypto`, …) | |
| ۶ | `listen_addresses` و `ssl` | |
| ۷ | `max_connections` و مصرف فعلی | |
| ۸ | سیاست پشتیبان واقعی و تازگی آن | |
| ۹ | فضای آزاد دیسک | |

> [!note] دو نمونه PostgreSQL در پیش‌بینی معماری
> طبق `META-INT-150` بند ۳، پایگاه‌داده **وب‌سایت/پلتفرم** از پایگاه‌داده **n8n** جداست. سامانه این پروژه به نمونه وب‌سایت/پلتفرم تعلق دارد، نه به نمونه n8n. اگر نمونه دوم هنوز ساخته نشده است، این یک **تصمیم و اقدام** است، نه یک یافته ممیزی — بند ۹.

## ۸. ریسک شماره یک: DNS و TLS

### ۸.۱. مسئله

WordPress روی هاست اشتراکی باید با **HTTPS معتبر** به Field API وصل شود. گواهی‌های معتبر عمومی برای «آدرس IP خالی» صادر نمی‌شوند (یا بسیار محدودند). بنابراین یک **نام میزبان** لازم است.

```text
WordPress (cPanel) ──HTTPS──▶ field.<domain> ──▶ Caddy ──▶ Field API
                                    ▲
                          نیازمند رکورد DNS + گواهی معتبر
```

### ۸.۲. گزینه‌ها

| گزینه | مزیت | ریسک/هزینه | توصیه |
|---|---|---|---|
| **A. زیردامنه روی دامنه موجود** (`field.xennic.ir`) | ساده‌ترین، TLS خودکار با Caddy، حرفه‌ای | نیاز به دسترسی DNS دامنه؛ دامنه فعلاً در جای دیگری استفاده می‌شود | ✅ **پیشنهاد اول** |
| B. دامنه ارزان/فرعی خریداری‌شده مخصوص سرور | استقلال از دامنه فعلی | هزینه کم، زمان انتشار DNS | گزینه پشتیبان |
| C. سرویس تونل (Cloudflare Tunnel یا مشابه) | بدون نیاز به باز کردن پورت، TLS مدیریت‌شده | وابستگی به سرویس بیرونی؛ ممکن است در ایران محدودیت دسترسی باشد | فقط در صورت بسته بودن پورت ۴۴۳ |
| D. گواهی self-signed | بدون نیاز به DNS | PHP به‌صورت پیش‌فرض رد می‌کند؛ غیرحرفه‌ای | ❌ رد |
| E. بدون پنل، فقط ربات | صفر وابستگی | از دست رفتن پنل تا پس از نمایشگاه | ✅ **مسیر جایگزین عملی** |

### ۸.۳. تصمیم پیشنهادی

> [!important] توصیه
> ۱) امروز رکورد `field` (یا نام مشابه) روی دامنه موجود ساخته و به IP عمومی سرور اشاره شود. ۲) Caddy با TLS خودکار راه‌اندازی شود. ۳) اگر تا ۲۴ ساعت پیش از نمایشگاه این مسیر آماده نشد، **پروژه متوقف نمی‌شود**: ربات بله با Polling کار می‌کند و پنل WordPress به نسخه پس از نمایشگاه منتقل می‌شود. این تصمیم در نود ۰۱۱ به‌صورت شرط پذیرش ثبت شده است.

## ۹. تصمیم‌های استقرار

| # | تصمیم | پیشنهاد | جایگزین |
|---|---|---|---|
| E-1 | نمونه PostgreSQL | همان نمونه **وب‌سایت/پلتفرم** (`META-INT-150` بند ۳)، نه نمونه n8n | اگر ساخته نشده: ساخت نمونه جدید با همان قواعد |
| E-2 | پایگاه‌داده یا Schema | یک پایگاه‌داده، Schemaهای `crm` و `iee1405` در آن | پایگاه‌داده مستقل `xennic_field` با همان Schemaها |
| E-3 | کاربر دیتابیس | کاربر اختصاصی `field_api` با مجوز فقط روی `crm`/`iee1405` و `SELECT` روی `shared` | — |
| E-4 | محل اجرای Field API | کانتینر `field-api` در همان پشته Compose | سرویس مستقل با Compose جدا |
| E-5 | محل ذخیره فایل | `/srv/xennic-field/uploads` روی همان دیسک NVMe | Volume جداگانه Docker |
| E-6 | Reverse Proxy | Caddy موجود/جدید با TLS خودکار | Nginx (در صورت وجود) |
| E-7 | دسترسی مدیریتی | فقط تونل SSH | VPN/Tailscale (فاز بعد) |
| E-8 | بکاپ | `pg_dump` روزانه + آرشیو فایل هفتگی، خارج از سرور | فقط روی همان سرور (رد می‌شود) |

> [!warning] قاعده D-1 در عمل
> اگر برای سرعت بخواهیم یک «دیتابیس موقت نمایشگاهی» بسازیم، دقیقاً همان چیزی را می‌سازیم که مأموریت منع کرده است. Schemaهای دائمی `crm`/`iee1405` حتی اگر بعداً تغییر کنند، **همان مسیر** را حفظ می‌کنند.
