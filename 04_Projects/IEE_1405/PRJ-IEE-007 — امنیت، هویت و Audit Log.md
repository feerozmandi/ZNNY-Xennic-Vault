## ۱. هدف (Why)

این سامانه، داده تجاری حساس نگه می‌دارد: نام و شماره مدیران شرکت‌ها، شرایط همکاری، قیمت‌های اعلامی، ارزیابی رقبا و یادداشت‌های داخلی. هم‌زمان، سطح حمله آن بالاست: یک سرور عمومی، یک هاست اشتراکی، یک ربات پیام‌رسان و دو گوشی همراه.

مأموریت، نُه الزام امنیتی صریح دارد (HTTPS، عدم دسترسی عمومی به پایگاه‌داده، احراز هویت و سطح‌بندی دسترسی، Audit Log، جلوگیری از بازنویسی، کنترل تعارض، پشتیبان و آزمون بازیابی، مدیریت امن فایل، عدم ذخیره راز در کد). این نود همه را در یک مدل واحد سازمان می‌دهد و به [[L2-SEC-001 — امنیت اطلاعات|L2-SEC-001]] و [[META-INT-100 — مدیریت Secrets و Credentials|META-INT-100]] متصل می‌کند — بدون تکرار محتوای آن‌ها.

> [!important] اصل تناسب
> امنیت باید متناسب با ریسک باشد. برای دو کاربر داخلی و یک نمایشگاه چهارروزه، پیاده‌سازی IAM سازمانی و HSM، اتلاف وقت است؛ اما توکن مشترک روی همه‌چیز و پایگاه‌داده با پورت باز، بی‌مسئولیتی است. این نود حد وسط را تعیین می‌کند.

## ۳. هویت و احراز هویت

### ۳.۱. انواع هویت در سامانه

| نوع هویت | شناسه | مکانیزم | مصرف‌کننده |
|---|---|---|---|
| کاربر انسانی | `user:<username>` | ورود WordPress (لایه اول) + `X-Actor-Id` | پنل |
| کاربر میدانی | `user:<username>` | `chat_id` ثبت‌شده در `crm.users` | ربات بله |
| سرویس | `service:wp`, `service:n8n` | توکن Bearer مستقل با دامنه مجاز | پنل، n8n |
| کاربر مهمان | — | بدون دسترسی | — |

### ۳.۲. قواعد توکن

| موضوع | قاعده |
|---|---|
| قالب | توکن تصادفی ۳۲ بایت (Base64URL)؛ ذخیره **فقط هش** (SHA-256) در پایگاه‌داده |
| تفکیک | یک توکن جداگانه برای WordPress، یکی برای n8n، یکی برای ربات (اختیاری، اگر Polling استفاده شود) |
| حداقل مجوز | هر توکن فقط Scopeهای لازم؛ `wp` اجازه `admin` ندارد |
| انقضا | ۹۰ روز؛ چرخش اجباری با دوره هم‌پوشانی ۲۴ ساعته |
| ابطال | فوری با `is_active=false` و ثبت `audit_event` |
| نمایش | هرگز کامل نمایش داده نمی‌شود؛ فقط ۶ کاراکتر آخر |

> [!note] چرا JWT در نسخه اول نیست؟
> پیچیدگی صدور/تمدید و مدیریت کلید، با دو کاربر و سه سرویس، توجیه ندارد. توکن بی‌حالت (Opaque Token) + جدول مجوز ساده‌تر و قابل ابطال‌تر است. مسیر ارتقا به OIDC/JWT باز می‌ماند.

## ۷. کنترل تعارض و جلوگیری از بازنویسی

### ۷.۱. چرخه ویرایش

```text
۱) کلاینت رکورد را با version دریافت می‌کند (مثلاً ۷)
۲) کاربر ویرایش می‌کند و PATCH با If-Match: 7 می‌فرستد
۳) سرور: UPDATE … WHERE id = :id AND version = 7
   ۴) یک ردیف تغییر کرد  → version=8، پاسخ 200 + audit_event
   ۵) صفر ردیف تغییر کرد → پاسخ 409 + نسخه فعلی + تفاضل فیلدها
۶) کلاینت تفاضل را نشان می‌دهد: «همکار شما هم‌زمان تغییر داده؛ کدام درست است؟»
```

### ۷.۲. قواعد مکمل

| # | قاعده |
|---|---|
| ۱ | درخواست `PATCH` بدون `If-Match` برای رکوردهای مهم (شرکت، مخاطب، ادعا) رد می‌شود |
| ۲ | `Idempotency-Key` اجباری برای همه `POST`؛ پاسخ تکرار، همان پاسخ اول است |
| ۳ | ادعای جاری، اتمیک جابه‌جا می‌شود (تراکنش + ایندکس یکتای جزئی) |
| ۴ | کاهش سطح اعتبار (مثلاً `verified` → `reported`) مجاز است اما با هشدار `downgrade` در Audit Log |
| ۵ | حذف، همیشه نرم است؛ `deleted_at` + دلیل |

> [!tip] چرا LWW ممنوع است؟
> «آخرین نوشته برنده» ساده‌ترین راه است و بدترین نتیجه را دارد: یادداشت یک نفر بی‌صدا حذف می‌شود. با توجه به اینکه دو گوشی هم‌زمان کار می‌کنند، تعارض **رخ می‌دهد**؛ بنابراین باید دیده شود، نه پنهان.

## ۸. History و Audit Log

### ۸.۱. ساختار

| ستون | توضیح |
|---|---|
| `id` | `bigserial` (ترتیب زمانی) |
| `occurred_at` | `timestamptz` سرور |
| `actor` | `user:…`, `service:…`, `system:…` |
| `action` | `create`, `update`, `delete`, `restore`, `login`, `export`, `token_rotate`, `approve` |
| `entity`, `entity_id` | موضوع رویداد |
| `before`, `after`, `diff` | JSONB؛ `diff` برای جست‌وجوی سریع |
| `request_id` | اتصال به درخواست API |
| `ip_hash` | هش IP (نه IP خام) برای رعایت حریم خصوصی |

### ۸.۲. قواعد

| # | قاعده |
|---|---|
| ۱ | جدول فقط افزودنی: هیچ `UPDATE`/`DELETE` مجاز نیست (مجوز دیتابیس این را تضمین می‌کند) |
| ۲ | ثبت در همان تراکنش تغییر اصلی — یعنی تغییری بدون رویداد وجود ندارد |
| ۳ | رویدادهای خواندن حساس (خروجی Excel، مشاهده فایل محرمانه) هم ثبت می‌شوند |
| ۴ | هر رویداد `request_id` دارد تا با لاگ سرویس قابل تطبیق باشد |
| ۵ | اثر انگشت روزانه: هش زنجیره‌ای انتهای هر روز در گزارش روزانه ثبت می‌شود |
| ۶ | نگهداشت: حداقل ۲۴ ماه؛ آرشیو ماهانه به فایل فشرده |

```sql
-- نمونه ساده «اثر انگشت روزانه» برای تشخیص دستکاری
SELECT date_trunc('day', occurred_at) AS day,
       count(*) AS events,
       encode(digest(string_agg(id::text || actor || action, '|' ORDER BY id), 'sha256'), 'hex') AS chain_hash
FROM crm.audit_events
GROUP BY 1 ORDER BY 1 DESC;
```

## ۹. فایل، پشتیبان و راز

| موضوع | قاعده |
|---|---|
| ذخیره فایل | `/srv/xennic-field/uploads/<year>/<month>/<uuid>.<ext>` — خارج از Webroot سرویس‌های عمومی |
| دسترسی | فقط با URL امضاشده کوتاه‌عمر (۵ دقیقه) از Field API |
| نام فایل | UUID؛ نام اصلی کاربر فقط در متادیتا |
| مجوز فایل | `0640`، مالکیت کاربر سرویس، بدون اجرا |
| آنتی‌ویروس | اختیاری در نسخه اول؛ در صورت افزودن، ClamAV در صف |
| پشتیبان | `pg_dump` روزانه + فایل‌ها هفتگی + رمزنگاری `age` + جداول بررسی |
| آزمون بازیابی | یک بار واقعی پیش از نمایشگاه (نود ۰۱۳) |
| راز | `.env` روی سرور با `0600`؛ نسخه در Password Manager مالک؛ بدون راز در Git/Vault/چت |

> [!warning] قاعده پشتیبان
> پشتیبانی که بازیابی آن آزمون نشده، پشتیبان نیست. آزمون بازیابی یک اقدام اجباری پیش از نمایشگاه است، نه یک کار «در صورت داشتن وقت».

## ۱۱. آزمون امنیتی و رویه رخداد

### ۱۱.۱. آزمون‌های الزامی پیش از نمایشگاه

| # | آزمون | معیار |
|---|---|---|
| ۱ | تماس از بیرون به پورت پایگاه‌داده | ناموفق |
| ۲ | درخواست بدون توکن به API | `401` |
| ۳ | درخواست با نقش ناکافی | `403` |
| ۴ | `PATCH` با نسخه قدیمی | `409` و عدم تغییر داده |
| ۵ | آپلود فایل اجرایی با پسوند `.jpg` | رد |
| ۶ | آپلود ۲۰ مگابایتی | رد با پیام واضح |
| ۷ | ورود به پنل با رمز اشتباه ۱۰ بار | قفل موقت/تأخیر |
| ۸ | جست‌وجوی Vault برای داده شرکت | هیچ نتیجه‌ای |
| ۹ | بازیابی پایگاه‌داده از پشتیبان | موفق و کامل |
| ۱۰ | چرخش توکن | سرویس‌ها بدون قطعی ادامه دهند |

### ۱۱.۲. رویه رخداد (Runbook کوتاه)

| موقعیت | اقدام فوری | اقدام بعدی |
|---|---|---|
| نشت توکن مشکوک | ابطال توکن + صدور توکن جدید + بررسی Audit Log | گزارش رخداد + بازبینی مسیر نشت |
| ورود غیرمجاز به پنل | تغییر رمز، غیرفعال‌سازی کاربر، بررسی لاگ | بازبینی افزونه‌ها، به‌روزرسانی |
| خرابی پایگاه‌داده | توقف نوشتن، بررسی دیسک/لاگ، بازیابی از پشتیبان | تحلیل ریشه‌ای + ثبت در گزارش |
| حذف اشتباه داده | توقف، بازیابی رکورد از `deleted_at` یا پشتیبان | پیشنهاد کنترل پیشگیرانه |
| اختلال در روز نمایشگاه | ادامه کار با ربات/آفلاین، ثبت در برگه کاغذی | ورود دسته‌ای پس از بازگشت سرویس |
