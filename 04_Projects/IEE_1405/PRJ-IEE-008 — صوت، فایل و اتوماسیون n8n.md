## ۱. هدف (Why)

در نمایشگاه، نوشتن یادداشت روی گوشی کوچک، کند و خطاپذیر است؛ اما **گفتن** آن، طبیعی و سریع است. به همین دلیل یادداشت صوتی، یکی از روش‌های اصلی ثبت در مأموریت است. مشکل اینجاست که صوت بدون رونویسی، در عمل قابل جست‌وجو و استفاده نیست؛ و رونویسی با سرویس ابری، داده تجاری حساس را از سرور بیرون می‌برد.

این نود سه مسئله را حل می‌کند:

1. **رونویسی محلی**: روی همان VPS، بدون ارسال صوت به سرویس بیرونی.
2. **مدیریت فایل**: نگهداری امن و قابل بازیابی عکس، صوت و کاتالوگ.
3. **اتوماسیون**: کارهای تکراری (پشتیبان، یادآوری، گزارش) که نباید در روز نمایشگاه انجام شوند.

> [!warning] محدودیت تعیین‌کننده
> سقف RAM سرور ۶ گیگابایت است و سرویس‌های فعلی (n8n، PostgreSQL، Qdrant، TEI، SurrealDB، Open Notebook) بخش قابل‌توجهی از آن را مصرف می‌کنند (تحلیل در `META-INT-140` بند ۲.۱). افزودن یک مدل گفتاری سنگین، بدون محاسبه، سرور را در بحرانی‌ترین روز از کار می‌اندازد.

## ۲. تصمیم‌های بنیادی پردازش

| # | تصمیم | انتخاب | دلیل |
|---|---|---|---|
| SD-1 | موتور رونویسی | `faster-whisper` (CTranslate2) روی CPU | سبک‌تر و سریع‌تر از `whisper` اصلی در همین سخت‌افزار |
| SD-2 | اندازه مدل | `small` با `compute_type=int8` | تعادل دقت/حافظه؛ `medium` به‌عنوان گزینه آزمایشی |
| SD-3 | محل اجرا | کانتینر مستقل `stt-worker` روی VPS | جداسازی مصرف حافظه و امکان توقف اضطراری |
| SD-4 | زمان پردازش | **پس از نمایشگاه به‌طور پیش‌فرض**؛ در حین نمایشگاه فقط با درخواست دستی | آزاد نگه‌داشتن RAM برای ربات و API |
| SD-5 | هم‌زمانی | ۱ کار در هر لحظه (Concurrency=1) | جلوگیری از فشار حافظه |
| SD-6 | ارسال به سرویس ابری | ممنوع در نسخه اول | محرمانگی داده تجاری |
| SD-7 | خروجی | متن خام + قطعه‌بندی زمانی + خلاصه پیشنهادی (پیشنهاد، نه حقیقت) | قابلیت بازبینی و جست‌وجو |
| SD-8 | ذخیره صوت | نگهداری اصلی؛ حذف اختیاری پس از رونویسی و تأیید | شاهد اصلی قابل حذف نیست مگر با تصمیم مالک |

> [!note] چرا `small` و نه `large`؟
> برای گفتار فارسی در محیط پرصدا (نمایشگاه)، مدل بزرگ‌تر لزوماً بهتر نیست؛ سرعت و پایداری مهم‌تر است و **بازبینی انسانی** بخشی از طراحی است. مدل `medium` می‌تواند در فاز دوم با اندازه‌گیری دقت واقعی ارزیابی شود.

## ۳. معماری صف و پردازش صوت

```text
ربات بله ──▶ Field API (ذخیره فایل + رکورد در crm.attachments)
                    │
                    ▼
          جدول iee1405.transcription_jobs
             status: queued | running | done | failed
                    │  (Polling توسط n8n)
                    ▼
        n8n [IEE-02] Transcribe Voice
             ├─ دریافت job
             ├─ فراخوانی stt-worker (HTTP داخلی)
             ├─ ذخیره متن در interaction.detail / field_notes.transcript
             ├─ درج خلاصه در crm.ai_suggestions (status=proposed)
             └─ به‌روزرسانی وضعیت job
```

| جزء | مسئولیت |
|---|---|
| `transcription_jobs` | صف پایدار؛ شامل `attachment_id`, `status`, `attempts`, `last_error`, `started_at`, `finished_at` |
| `stt-worker` | سرویس HTTP کوچک: دریافت مسیر فایل → خروجی JSON (متن، قطعات، زبان) |
| n8n | هماهنگ‌کننده؛ نه پردازش‌کننده |
| Field API | دریافت نتیجه، اعتبارسنجی، ثبت ادعا/پیشنهاد، ثبت رویداد |

> [!important] قاعده «صف پایدار، نه پیام در حافظه»
> اگر سرویس در میانه رونویسی ری‌استارت شود، Job نباید گم شود. به همین دلیل صف در پایگاه‌داده است، نه در حافظه یا RabbitMQ.

## ۴. کیفیت رونویسی فارسی

| # | اقدام | اثر |

## ۵. مدیریت فایل و کاتالوگ

### ۵.۱. چیدمان ذخیره‌سازی

```text
/srv/xennic-field/
├── uploads/
│   ├── 2026/11/
│   │   ├── 0f3a…-photo.jpg
│   │   ├── 7c21…-voice.ogg
│   │   └── 9b04…-catalog.pdf
├── tmp/                     ← فقط برای پردازش؛ پاک‌سازی روزانه
├── backups/
│   ├── db/                  ← pg_dump رمزنگاری‌شده
│   └── files/               ← آرشیو هفتگی
└── logs/
```

| موضوع | قاعده |
|---|---|
| نام | UUID + پسوند اصلی؛ هیچ‌گاه نام کاربر به‌عنوان مسیر |
| هش | SHA-256 یکتا؛ آپلود تکراری، فایل جدید نمی‌سازد |
| متادیتا | `crm.attachments` (نوع، اندازه، مدت، اتصال به موجودیت) |
| دسترسی | فقط URL امضاشده کوتاه‌عمر؛ بدون سرو استاتیک عمومی |
| پاک‌سازی | `tmp/` روزانه؛ فایل‌های بدون متادیتا پس از ۷ روز |
| کاتالوگ PDF | ذخیره و ایندکس متنی (در فاز دوم با OCR) |
| ظرفیت | پایش هفتگی؛ هشدار در ۷۰٪ دیسک |

### ۵.۲. فراداده حداقلی هر فایل

| فیلد | مثال |
|---|---|
| `kind` | `photo` / `audio` / `catalog` / `scan` |
| `sha256` | `b1946ac9…` |
| `mime` | `image/jpeg` |
| `size_bytes` | `1_845_223` |
| `duration_sec` | برای صوت |
| `linked_entity` + `linked_id` | `organization` / `ORG-000123` |
| `captured_at` | زمان واقعی روی گوشی |
| `uploaded_by` | عامل |
| `privacy_flag` | `gps_removed`, `face_present`, `consent_recorded` |

## ۶. بودجه منابع و ظرفیت سرور

| سرویس | مصرف تقریبی RAM | ملاحظه |
|---|---|---|
| سیستم‌عامل + Docker | ۴۰۰ تا ۶۰۰ مگابایت | ثابت |
| n8n | ۳۰۰ تا ۵۰۰ مگابایت | ثابت |
| PostgreSQL (n8n) | ۱۰۰ تا ۲۰۰ مگابایت | ثابت |
| Qdrant | ۱۵۰ تا ۲۵۰ مگابایت | ثابت |
| TEI Embedding | ۱٬۰۰۰ تا ۱٬۵۰۰ مگابایت | **سنگین‌ترین سرویس موجود** |
| Open Notebook + SurrealDB | ۴۰۰ تا ۷۰۰ مگابایت | ثابت |
| Field API (ربات + REST) | ۲۰۰ تا ۴۰۰ مگابایت | متغیر با بار |
| **stt-worker (faster-whisper small, int8)** | **۵۰۰ تا ۱٬۰۰۰ مگابایت** | فقط هنگام پردازش |
| Caddy | < ۵۰ مگابایت | ثابت |
| **مجموع در اوج** | **حدود ۳.۵ تا ۵.۵ گیگابایت از ۶** | حاشیه کم |

> [!warning] نتیجه‌گیری سخت‌گیرانه
> در حین نمایشگاه، مدل گفتاری **نباید** به‌صورت پیش‌فرض روشن باشد. اگر لازم شد، ابتدا `TEI` به‌صورت موقت متوقف می‌شود (چون در نمایشگاه به آن نیازی نیست)، سپس `stt-worker` اجرا می‌شود. این رویه در Runbook روز نمایشگاه ثبت می‌شود.

```bash
# رویه اضطراری (نمونه — اجرا فقط با تصمیم مالک)
docker stop xennic-tei          # آزادسازی ~۱ تا ۱.۵ گیگابایت
docker start xennic-stt         # راه‌اندازی موقت رونویسی
# پس از پایان: توقف stt و راه‌اندازی مجدد TEI
```

> [!note] گزینه جایگزین بدون فشار بر سرور
> اگر پردازش پس از نمایشگاه با حجم زیاد صوت روبرو شد، می‌توان رونویسی را روی لپ‌تاپ مالک (خارج از سرور) انجام و نتیجه را از طریق API وارد کرد. این گزینه در نود ۰۱۳ به‌عنوان مسیر پشتیبان ثبت شده است.

## ۷. Workflowهای n8n

| شناسه | نام | Trigger | هدف | ورودی | خروجی |
|---|---|---|---|---|---|
| `[IEE-01]` | Booth Brief Digest | Schedule (۰۷:۳۰) | ارسال فهرست برگه‌های پیش‌بازدید روز از طریق بله | `GET /brief/today` | پیام بله + ثبت ارسال |
| `[IEE-02]` | Transcribe Voice | Schedule (هر ۱۵ دقیقه) یا Manual | رونویسی صف صوت | `transcription_jobs` | متن + پیشنهاد خلاصه |
| `[IEE-03]` | Nightly Export & Backup | Schedule (۲۳:۳۰) | `pg_dump` + خروجی Excel روز + هش | پایگاه‌داده | فایل پشتیبان + پیام وضعیت |
| `[IEE-04]` | Daily Reminder | Schedule (۰۸:۰۰ و ۱۹:۰۰) | یادآوری وظایف باز و ثبت‌های ناقص | `GET /tasks/open` | پیام بله |
| `[IEE-05]` | Knowledge Index | Schedule (هفتگی) | ایندکس خلاصه‌های تأییدشده در Qdrant برای RAG | جدول `interactions` تأییدشده | Point در Qdrant |

### ۷.۱. قواعد ثبت و حاکمیت

| # | قاعده |
|---|---|
| ۱ | هر Workflow بلافاصله پس از ساخت در [[META-INT-090 — رجیستری Workflowهای n8n\|META-INT-090]] با نام، شناسه فنی، Trigger و مالک ثبت می‌شود |
| ۲ | شناسه نمایشی با پیشوند `[IEE-xx]`؛ نام Credential هرگز در Vault نوشته نمی‌شود (فقط نام حساب) |
| ۳ | Trigger پیش‌فرض: `Schedule` با زمان تهران؛ `Manual` برای موارد حساس |
| ۴ | هر Workflow باید «اجرای دوباره ایمن» باشد (Idempotent): اجرای دوباره، رکورد تکراری نسازد |
| ۵ | خروجی هر اجرا در لاگ n8n با `request_id` قابل تطبیق با Field API باشد |

### ۷.۲. نمونه منطق `[IEE-03]`

```text
Schedule 23:30 → Field API: GET /exports/export.xlsx?date=today
   → ذخیره فایل با تاریخ در backups/exports
   → اجرای pg_dump (فشرده) → رمزنگاری age → checksum
   → ارسال پیام وضعیت به بله (حجم، مدت، موفق/ناموفق)
   → در صورت خطا: تلاش مجدد با فاصله ۱۰ دقیقه (حداکثر ۳ بار)
```

## ۸. خطا، تلاش مجدد و صف ناموفق

| وضعیت | رفتار |
|---|---|
| خطای شبکه موقت | تلاش مجدد با تأخیر پرشی: ۳۰ ثانیه، ۲ دقیقه، ۱۰ دقیقه |
| خطای دائمی (فایل خراب) | `status=failed` + دلیل + اعلان به مالک |
| بیش از ۳ تلاش | انتقال به «صف نیازمند بررسی» و توقف خودکار |
| تکرار اجرا | کلید Idempotency بر اساس `attachment_id` یا تاریخ روز |
| خطای دسترسی | توقف و هشدار فوری (نه تلاش مجدد) |

> [!important] قاعده «شکست صدادار»
> هیچ Workflowای نباید بی‌صدا شکست بخورد. هر شکست، یک پیام در بله و یک رکورد در جدول `workflow_failures` دارد. سکوت در اتوماسیون، خطرناک‌تر از خطاست.
