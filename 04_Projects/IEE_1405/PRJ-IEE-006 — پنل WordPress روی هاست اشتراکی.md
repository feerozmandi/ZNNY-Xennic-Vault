## ۱. هدف (Why)

مأموریت، WordPress را به‌عنوان «رابط کاربری و داشبورد مدیریتی» و در عین حال **بدون اتصال مستقیم به PostgreSQL** تعیین کرده است. این ترکیب، در نگاه اول متناقض به‌نظر می‌رسد؛ اما کاملاً منطقی است: داده در یک جای معتبر (PostgreSQL روی VPS) می‌ماند و WordPress فقط **پنجره‌ای** به آن داده است.

سه دلیل انتخاب این معماری:

| دلیل | توضیح |
|---|---|
| زیرساخت موجود | هاست اشتراکی cPanel از قبل در اختیار است؛ نیازی به سرور اضافه نیست |
| سرعت راه‌اندازی | ساخت پنل در WordPress سریع‌تر از ساخت یک SPA اختصاصی است |
| جدایی داده از رابط | با حذف یا خرابی WordPress، هیچ داده‌ای از دست نمی‌رود |

> [!warning] هزینه این انتخاب
> هاست اشتراکی، محیط محدودی است: PHP، بدون Node/Python، اغلب بدون افزونه PostgreSQL، با محدودیت CPU/RAM و گاهی با ModSecurity سخت‌گیر. همه محدودیت‌ها در بند ۲ آمده و طراحی بر اساس آن‌ها انجام شده است.

## ۲. محدودیت‌های هاست اشتراکی

| # | محدودیت | پیامد طراحی |
|---|---|---|
| ۱ | فقط PHP (و معمولاً بدون Python/Node پایدار) | منطق در Field API، پنل فقط PHP ساده |
| ۲ | افزونه `pgsql`/`pdo_pgsql` معمولاً نصب نیست | تأیید D-2؛ اتصال مستقیم حتی اگر خواستند، ممکن نیست |
| ۳ | بدون دسترسی SSH در برخی پلن‌ها | استقرار با آپلود ZIP از مدیر فایل |
| ۴ | `WP-Cron` وابسته به ترافیک و نامطمئن | استفاده از Cron واقعی cPanel یا اجرای دستی |
| ۵ | محدودیت `max_execution_time` (اغلب ۳۰ تا ۶۰ ثانیه) | همه عملیات شبکه کوتاه؛ خروجی بزرگ به‌صورت Stream |
| ۶ | محدودیت حافظه (اغلب ۲۵۶ مگابایت) | صفحه‌بندی سمت سرور؛ بدون بارگذاری کل مجموعه |
| ۷ | ModSecurity ممکن است درخواست خروجی را مسدود کند | استفاده از `wp_remote_request` استاندارد؛ در صورت بلاک، افزودن User-Agent مشخص |
| ۸ | IP خروجی مشترک و متغیر | عدم استفاده از IP-allowlist به‌عنوان تنها لایه امنیتی؛ توکن + محدودیت نرخ |
| ۹ | HTTPS سایت به گواهی هاست وابسته است | اجباری بودن `force_ssl_admin` و بررسی گواهی در سمت PHP (`sslverify => true`) |
| ۱۰ | به‌روزرسانی‌های WordPress و افزونه‌ها | پلاگین بدون وابستگی بیرونی؛ برنامه به‌روزرسانی دوره‌ای |

│   └── class-export.php          ← ساخت خروجی CSV/XLSX از API

### ۳.۲. اصول پیاده‌سازی

| # | اصل |
|---|---|
| ۱ | **بدون ACF، بدون Elementor، بدون Page Builder** — فرم‌های بومی WordPress |
| ۲ | بدون کامپایل React/Vue در نسخه اول (حذف وابستگی ابزار ساخت) |
| ۳ | هر درخواست به API با بررسی `wp_remote_request` و زمان‌سنجی |
| ۴ | همه فرم‌ها با `nonce` و `current_user_can()` محافظت می‌شوند |
| ۵ | هیچ منطق اعتبارسنجی دامنه در PHP تکرار نمی‌شود (D-2) |
| ۶ | همه خروجی‌های HTML با `esc_html`/`esc_attr`/`wp_kses_post` |
| ۷ | کد در مخزن `feerozmandi/xennic-field-panel` نسخه‌دار و با ZIP منتشر می‌شود |

> [!note] چرا پلاگین و نه Child Theme؟
> پنل باید مستقل از قالب سایت باشد و با تغییر تم، از کار نیفتد. پلاگین همچنین امکان فعال/غیرفعال‌سازی فوری در شرایط اضطراری را می‌دهد.

## ۴. احراز هویت و کنترل دسترسی

### ۴.۱. دو لایه مستقل

| لایه | چه چیزی را کنترل می‌کند | محل |
|---|---|---|
| لایه WordPress | ورود به پنل، نقش، عملیات مجاز در رابط | MySQL هاست |
| لایه Field API | هویت واقعی عامل، سطح دسترسی، مالکیت داده | PostgreSQL + توکن |

> [!important] قاعده «هویت دوگانه»
> هر درخواست از پنل، هم توکن سرویس (`wp_service`) و هم شناسه عامل (`X-Actor-Id`) را می‌فرستد. Field API بررسی می‌کند که این عامل مجاز به آن عملیات هست یا نه. یعنی حتی اگر حساب WordPress به‌سرقت برود، سطح خسارت به مجوزهای همان عامل محدود می‌ماند.

### ۴.۲. نقش‌ها و Capabilityها

| نقش WordPress | Capabilityهای اختصاصی | دسترسی در Field API |
|---|---|---|
| `administrator` | `xennic_view`, `xennic_edit`, `xennic_export`, `xennic_admin` | `owner` (کامل) |
| `xennic_manager` (نقش سفارشی) | `xennic_view`, `xennic_edit`, `xennic_export` | `analyst` |
| `xennic_viewer` (نقش سفارشی) | `xennic_view` | `viewer` (فقط خواندن) |
| — | — | `field_agent` فقط از ربات بله |

### ۴.۳. ذخیره توکن

| موضوع | قاعده |
|---|---|
| محل توکن | ثابت `XENNIC_FIELD_TOKEN` در `wp-config.php` (خارج از پوشه پلاگین و خارج از Git) |
| جایگزین | گزینه رمزنگاری‌شده با `AUTH_KEY` در صورت عدم دسترسی به `wp-config.php` |
| نمایش در UI | هرگز؛ فقط «متصل / قطع» و زمان آخرین تماس موفق |
| چرخش | توکن دوگانه با دوره هم‌پوشانی ۲۴ ساعته؛ رویه در `META-INT-100` |
| لاگ | توکن در لاگ و پیام خطا ماسک می‌شود |

## ۵. ارتباط با Field API

### ۵.۱. کلاینت HTTP

```php
// نمونه کوتاه — منطق واقعی در class-api-client.php
$response = wp_remote_request(
    XENNIC_FIELD_BASE . '/api/v1/organizations?page=1&per_page=25',
    [
        'method'    => 'GET',
        'timeout'   => 12,
        'sslverify' => true,
        'headers'   => [
            'Authorization' => 'Bearer ' . XENNIC_FIELD_TOKEN,
            'X-Actor-Id'    => 'wp:' . wp_get_current_user()->user_login,
            'Accept'        => 'application/json',
            'User-Agent'    => 'XennicFieldPanel/0.1 (+cpanel)',
        ],
    ]
);
if (is_wp_error($response)) { /* نمایش خطای شبکه با پیام کوتاه */ }
$code = wp_remote_retrieve_response_code($response);
$body = json_decode(wp_remote_retrieve_body($response), true);
```

### ۵.۲. قواعد تماس

| موضوع | قاعده |
|---|---|
| تعداد درخواست در هر صفحه | ۱ تا ۳ درخواست (فهرست + شمارش)، نه بیشتر |
| زمان‌سنجی | ۱۲ ثانیه؛ در صورت خطا، تلاش دوم با فاصله ۱ ثانیه |
| کش | ۶۰ ثانیه برای فهرست‌ها، بدون کش برای پرونده در حال ویرایش |
| صفحه‌بندی | سمت سرور API؛ حداکثر ۲۵ ردیف در هر صفحه |
| ویرایش | `PATCH` با `If-Match: <version>`؛ در تعارض، نمایش تفاضل و انتخاب کاربر |
| خطا | نمایش پیام فارسی + کد پیگیری، بدون نمایش پاسخ خام API |

## ۸. دامنه نسخه نمایشگاه (MVP)

| قابلیت | در نسخه نمایشگاه | دلیل |
|---|---|---|
| مشاهده همه موجودیت‌ها | ✅ | لازم برای بازبینی روز |
| ویرایش فیلدهای پایه شرکت و مخاطب | ✅ | تکمیل تدریجی پرونده |
| افزودن ادعا با منبع | ✅ | هسته صداقت داده |
| افزودن تعامل و وظیفه | ✅ | پیگیری |
| خروجی CSV/Excel | ✅ | درخواست صریح مأموریت |
| مدیریت فرصت‌ها با گردش تأیید | ⏳ | زمان‌بر؛ در نسخه دوم |
| آپلود فایل از پنل | ⏳ | ربات کافی است |
| داشبورد تحلیلی و نمودار | ⏳ | پس از نمایشگاه |

> [!warning] قاعده «پنل، ربات را جایگزین نمی‌کند»
> در نمایشگاه، ثبت اولیه با ربات انجام می‌شود. پنل برای **بازبینی، تکمیل و گزارش** است. اگر پنل در روز نمایشگاه از دسترس خارج شد، کار متوقف نمی‌شود — این تعریف عملی «تحمل شکست».
