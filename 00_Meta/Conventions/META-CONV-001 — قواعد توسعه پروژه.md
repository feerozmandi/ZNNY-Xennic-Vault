# META-CONV-001 — قواعد توسعه پروژه

> [!abstract] هدف
> این سند مرجع رسمی تمام قواعد، روش‌ها، استانداردها و تصمیم‌های حاکم بر توسعه Vault شرکت **زر نور نیرو یکتا (Xennic)** است.
> هر توسعه‌دهنده جدید، **قبل از شروع کار** باید این سند را مطالعه کند.

> [!tip] خلاصه سریع
> - هیچ کامیتی مستقیم روی `main` یا `dev` نیست؛ همه تغییرات از طریق PR.
> - هر شاخه فقط یک نود دارد.
> - پیام کامیت و عنوان PR به انگلیسی و با الگوی `<type>(<NODE-ID>): <description>` است.
> - هیچ نودی مستقیم `approved` نمی‌شود؛ مسیر: `draft → review → approved → archived`.
> - فایل‌ها UTF-8 بدون BOM هستند و frontmatter باید در خط اول باشد.

## قاعده ۱ — ساختار Git Flow و PR اجباری

### شاخه‌ها

| شاخه | هدف | قواعد |
|---|---|---|
| `main` | نسخه پایدار | فقط از `dev` از طریق PR |
| `dev` | شاخه توسعه اصلی | فقط از `feature/*` از طریق PR |
| `feature/<NODE-ID>-<slug>` | یک نود یا قابلیت | فقط یک نود در هر شاخه |

> [!warning] قواعد PR (اجباری)
> - هیچ کامیتی مستقیم روی `main` مجاز نیست.
> - هیچ کامیتی مستقیم روی `dev` مجاز نیست.
> - همه تغییرات باید از طریق Pull Request ادغام شوند.
> - حتی برای اصلاح یک غلط املایی، PR الزامی است.
> - در پروژه‌های کوچک (توسعه‌دهنده واحد) می‌توان PR ساخت و خود Merge کرد.
> - در پروژه‌های تیمی حداقل **یک بازبین (Reviewer)** الزامی است.

### چرخه کار استاندارد

```bash
git checkout dev
git pull origin dev
git checkout -b feature/FND-XXX-slug
# کار روی نود
git add .
git commit -m "founder(FND-XXX): description"
git push -u origin feature/FND-XXX-slug
```

1. در GitHub: **Create Pull Request** با `base: dev ← compare: feature/FND-XXX-slug`
2. بازبینی و تأیید
3. Merge PR در GitHub
4. حذف شاخه feature (از GitHub یا محلی)
5. بازگشت به dev:

```bash
git checkout dev
git pull origin dev
```

### قواعد نام‌گذاری PR

**عنوان PR:** `<type>(<NODE-ID>): <description>`

```text
founder(FND-002): add distribution operations experience
docs(META-CONV-001): add mandatory PR rule
```

### قواعد توضیحات PR

هر PR باید شامل این بخش‌ها باشد:

- **What:** چه چیزی تغییر کرد
- **Why:** چرا
- **References:** ارجاع به NODE-ID یا Issue مرتبط
- **Checklist:** چک‌لیست بازبینی

> [!important] frontmatter باید **در خط اول فایل** و بین دو خط `---` باشد. هیچ خط یا فاصله‌ای قبل از آن مجاز نیست.

## قاعده ۷ — مستندسازی در Obsidian

### اصول

- همه نودها در Obsidian نوشته می‌شوند.
- فایل‌های Markdown با **UTF-8 بدون BOM** ذخیره می‌شوند.
- اتصال نودها با `[[wiki-link]]` و با نام کامل فایل انجام می‌شود، مثلاً `[[FND-001 — رزومه حرفه‌ای مهندسی]]`.
- متادیتا فقط در **frontmatter** نوشته می‌شود، نه در متن بدنه.
- هر نود در پوشه لایه خود قرار می‌گیرد.
- **ضمیمه‌ها در Open Notebook نگهداری می‌شوند:** PDFها، اسناد شرکت، لوگوها و تصاویر در Open Notebook ذخیره می‌شوند، نه در Git.
- در نود، ارجاع به ضمیمه به‌صورت متن ساده و با نام کامل فایل و نام Notebook نوشته می‌شود، مثلاً `Open Notebook: <نام Notebook> / <نام فایل>`.
- پوشه `attachments/` در مخزن ساخته نمی‌شود.

### ابزار

| ابزار | کاربرد |
|---|---|
| Obsidian | نوشتن، Graph و لینک‌ها |
| VS Code | ویرایش حرفه‌ای و جستجو |

## قاعده ۱۶ — نام‌گذاری فایل‌ها

### الگو

```text
<ID> — <title>.md
```

### قواعد

- جداکننده: `—` (em-dash، کاراکتر U+2014).
- یک فاصله قبل و بعد از جداکننده.
- عنوان: فارسی، بدون کاراکتر خاص.
- پسوند: `.md` (با حروف کوچک).

| وضعیت | مثال |
|---|---|
| ✅ درست | `FND-001 — رزومه حرفه‌ای مهندسی.md` |
| ❌ غلط | `FND-001 -- رزومه حرفه‌ای مهندسی.md` |
| ❌ غلط | `FND-001 - رزومه حرفه‌ای مهندسی.md` |

> [!tip] چرا em-dash؟
> - زیبایی بصری در Obsidian
> - استاندارد در مستندسازی حرفه‌ای
> - یکسان‌سازی همه فایل‌ها

> [!note] نکته
> در PowerShell برای تایپ em-dash از `Alt+0151` روی نام‌پد استفاده کنید، یا از Obsidian/VS Code کپی کنید.

## قاعده ۱۷ — ظاهر و خوانایی نود (UI/UX)

هر نود باید علاوه بر محتوای درست، **ظاهر تمیز، یکدست و خوانا** داشته باشد. الگوی مرجع همین سند (META-CONV-001) است.

### اجزای اجباری

1. **Callout چکیده** بلافاصله بعد از عنوان (H1):
   ```text
   > [!abstract] هدف
   > [یک یا دو جمله مستقل که هدف نود را خلاصه می‌کند]
   ```
2. **فهرست (TOC)** برای نودهایی که ۶ بخش `##` یا بیشتر دارند — جدول دوستونه (`# | بخش`) برای حداکثر ۸ بخش، یا جدول چهارستونه جفتی (`# | بخش | # | بخش`) برای بیش از ۸ بخش.
3. **خط جداکننده (`---`)** پیش از هر عنوان `##` به‌جز اولین عنوان بعد از چکیده/فهرست — برای جداسازی بصری بخش‌ها.
4. **Callout های محتوایی** (`[!note]`, `[!tip]`, `[!warning]`, `[!important]`) به‌جای تأکید ساده با `**نکته**:` یا `**توجه**:` برای نکات مستقل (نه داخل جدول یا لیست).
5. **Changelog پررنگ**: هر ردیف به‌صورت `- **vX.Y.Z (تاریخ):** توضیح`.

### قواعد ایمنی تغییر

- این قالب **افزایشی** است: عنوان‌ها، شماره‌گذاری بخش‌ها و محتوای موجود حذف یا جابه‌جا نمی‌شوند؛ فقط Callout، فهرست و خطوط جداکننده اضافه می‌شوند.
- اگر نودی از قبل خط جداکننده بین بخش‌ها دارد، جداکننده تکراری اضافه نمی‌شود.
- قالب [[node-template]] از ابتدا بر اساس همین قاعده ساخته می‌شود.

> [!tip] نمونه
> برای نمونه کامل اجرای این قاعده، به ساختار همین نود (META-CONV-001) یا هر نود دیگر در `01_Founder/`، `02_PreLaunch/`، `03_Launch/` مراجعه کنید.
