## قواعد استفاده (SOP)

1. **هرگز ID را دستی در کد وارد نکنید** — همیشه از این نقشه یا فایل JSON بخوانید.
    
2. **در صورت حذف و ایجاد مجدد Notebook**، این نود و فایل JSON باید **همزمان** به‌روزرسانی شوند (نسخه را افزایش دهید).
    
3. **نام کلیدها (Key) ثابت است** — حتی اگر نام نمایشی Notebook تغییر کند، کلیدها تغییر نمی‌کنند تا وابستگی‌ها نشکنند.
    
4. **دسترسی به `Corporate`** فقط با مدل محلی (Ollama) — هرگز به API خارجی ارسال نشود (طبق قاعده [[META-INT-040 — قواعد تفکیک محتوا (جلوگیری از موازی‌کاری)|META-INT-040]]).

  - این نتیجه، اجرای سیاست پیشنهادی در مدل آفلاین است؛ نه تصویب سیاست Production، نه احراز هویت واقعی، نه اثبات تشخیص restore و نه تضمین exactly-once. **ON-U08 در Runtime باز است.** استقراری انجام نشد.
- **v1.1.6 (۱۴۰۵-۰۸-۲۹):** ثبت سیاست پیشنهادی توسعهٔ Open Notebook؛ این ثبت سیاست پیشنهادی/وضعیت توسعه است و نقشهٔ شناسه‌ها/قرارداد دادهٔ این نود را تغییر نمی‌دهد. **ON-U16 — سیاست پیشنهادی بازصف‌گذاری اعلان با نتیجهٔ نامعلوم**
  - قاعدهٔ پیش‌فرض: restart، replay، timeout، نبود رکورد گیرنده یا پاسخ غیرقابل‌تطبیق، هیچ‌کدام `unknown` را خودکار به `pending` برنمی‌گردانند.
  - استثنای پیشنهادی: فقط اپراتوری با اختیار صریح مالک بتواند برای یک اعلان مشخص و همان `attempt` نامعلوم، یک بار بازصف‌گذاری را تأیید کند. ثبت دلیل و پذیرش صریح احتمال پیام تکراری الزامی است. اگر تازگی وضعیت فرستنده پس از restore محل تردید باشد، این استثنا تا تعیین تکلیف سابقه قابل استفاده نیست.
  - شرط ثبت: شناسهٔ تصمیم، هویت اپراتور، زمان UTC، `(dest, source)`، `attempt` قبلی، دلیل و پذیرش ریسک ثبت شوند؛ بدون متن پیام یا Secret. ثبت تصمیم و گذار `unknown → pending` باید با هم موفق شوند یا هیچ‌کدام اعمال نشوند.
  - اثر تصمیم: خودِ تأیید، پیام ارسال نمی‌کند. worker در زمان تصاحب `pending` یک `attempt` تازه می‌سازد. تکرار همان تصمیم یا تأیید هم‌زمان برای `attempt` قبلی نباید فرصت ارسال دوم بسازد. پاسخ دیررس `attempt` قبلی نیز نباید نتیجهٔ تلاش جدید را تغییر دهد.
  - این سیاست پیشنهادی است؛ به‌خودیِ‌خود Runtime، exactly-once یا آمادگی Production را تأیید نمی‌کند. **ON-U08 در Runtime باز است.** هیچ تغییر یا استقرار عملیاتی انجام نشد.

  - قرارداد اعلان ثبت‌شده در `n8n/tests/local-unit-result.md` طبق رفتار واقعی مدل: کلید رفع تکرار محلی `(dest, source)` است؛ پیش از ارسال، یک worker وضعیت را به‌صورت اتمی از `pending` به `unknown` می‌برد؛ فقط پاسخ قطعی همان تلاش می‌تواند وضعیت را به `delivered` یا `failed` تغییر دهد؛ اگر فرایند متوقف شود یا تأیید دریافت نرسد، وضعیت `unknown` باقی می‌ماند و راه‌اندازی مجدد باعث ارسال دوباره نمی‌شود. این رفتار از ارسال مجدد کور جلوگیری می‌کند؛ تحویل دقیقاً یک‌بار را تضمین نمی‌کند.
  - **ON-U08 — باز در Runtime.** نتیجهٔ ON-U11 نه تأیید اجرای واقعی است، نه تضمین exactly-once و نه اعلام آمادگی برای Production. هیچ تغییری در Workflow، VPS، n8n، Open Notebook یا Backup اعمال نشد.
