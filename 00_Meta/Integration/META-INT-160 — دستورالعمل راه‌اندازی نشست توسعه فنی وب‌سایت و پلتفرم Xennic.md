## ۱. هدف (Why)

این نود، **پرامپت رسمی و کامل راه‌اندازی** هر نشست جدید Arena (یا هر عامل هوش مصنوعی کدنویس دیگر) است که قرار است روی مخزن کد `feerozmandi/xennic-website` کار کند؛ شامل فهرست دقیق مستندات مرجع برای مطالعه اجباری، قواعد Git/دامنه/امنیت مخصوص مخزن کد، و متن کامل و آماده کپی‌کردن پرامپت شروع نشست.

این نود از نیاز مالک به داشتن یک **پل مستند و تکرارپذیر** بین Vault مستندات (`ZNNY-Xennic-Vault`) و مخزن کد مستقل (`xennic-website`) پدید آمده است: چون طبق [[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]] (بند ۱۲)، هر نشست Arena فقط روی یک مخزن کار می‌کند، نشست توسعه فنی باید از صفر و بدون دسترسی زنده به این Vault شروع شود؛ این نود تضمین می‌کند آن نشست، بدون حدس‌زنی یا بازتولید اشتباهات مخزن قدیمی رهاشده (طبق ممیزی `META-INT-150` بند ۸)، دقیقاً همان تصمیمات مصوب را اجرا کند.

این نود:
- مرجع رسمی و **تکرارپذیر** برای راه‌اندازی هر نشست توسعه آینده روی `xennic-website` (و در آینده، در صورت نیاز، مخازن مشابه برای فروشگاه یا مشاوره).
- پل مستند بین حاکمیت/تصمیمات (این Vault) و اجرای فنی (مخزن کد مستقل).
- چک‌لیست تأیید پیش از شروع کدنویسی واقعی.

**رابطه با نودهای دیگر**:
- [[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]]: سند مادر تصمیمات معماری که این دستورالعمل صرفاً روش اجرای آن در یک نشست جداگانه را مستند می‌کند.
- [[META-CONV-001 — قواعد توسعه پروژه|META-CONV-001]]: مرجع قواعد کلی Vault؛ بخش ۴ همین نود نسخه تطبیق‌یافته آن برای یک مخزن کد (نه Markdown/Obsidian) است.
- [[META-INT-100 — مدیریت Secrets و Credentials|META-INT-100]]، [[META-INT-140 — نقشه مهاجرت زیرساخت اتوماسیون به سرور اختصاصی (VPS)|META-INT-140]]: سیاست‌های امنیت و زیرساختی که نشست توسعه باید رعایت کند.
- [[L2-MKT-002 — طرح اجرایی و معماری وب‌سایت حرفه‌ای Xennic|L2-MKT-002]]، [[L2-MKT-003 — سیستم طراحی (Design System) وب‌سایت Xennic|L2-MKT-003]]، [[L2-MKT-004 — محتوای صفحات نسخه نخست وب‌سایت|L2-MKT-004]]، [[L2-MKT-005 — معماری فنی و CMS نهایی وب‌سایت Xennic|L2-MKT-005]]: مستندات اجرایی/محتوایی/فنی که مطالعه کامل آن‌ها پیش‌نیاز قطعی شروع کدنویسی است.

## ۲. دامنه و مخاطب این دستورالعمل

مخاطب این نود، **عامل هوش مصنوعی** (یا توسعه‌دهنده انسانی) است که در یک نشست Arena جدید، متصل به مخزن `feerozmandi/xennic-website`، کار توسعه را آغاز می‌کند — نه مخاطب این Vault. به همین دلیل، بخش ۱۰ این نود به‌صورت یک پرامپت مستقل و خودکفا نوشته شده که می‌تواند عیناً به‌عنوان اولین پیام آن نشست کپی و ارسال شود.

این دستورالعمل جایگزین مطالعه کامل مستندات اصلی **نیست** — فقط مسیر و ترتیب مطالعه را مشخص می‌کند. عامل توسعه در نشست جدید همچنان موظف است خودِ اسناد اصلی (نه خلاصه این نود) را به‌طور کامل بخواند.

## ۳. مرحله صفر: مطالعه اجباری Vault

پیش از هر خط کد، نشست جدید باید یک کپی فقط‌خواندنی از این Vault را در مسیری **کاملاً جدا از ریشه مخزن کد** Clone کند (دقیقاً به همان روشی که در همین Vault، هنگام ممیزی مخزن قدیمی `feerozmandiha/xennic`، عمل شد — نگاه کنید به [[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]] بند ۸) و فایل‌های فهرست‌شده در بند ۱۰ (بخش «اقدام اجباری اول») را به ترتیب اولویت بخواند.

> [!warning] این Vault هرگز بخشی از مخزن کد نمی‌شود
> مخزن `ZNNY-Xennic-Vault` فقط برای **خواندن مرجع** Clone می‌شود؛ هیچ تغییری در آن اعمال یا کامیت نمی‌شود و پوشه Clone آن هرگز به مخزن `xennic-website` اضافه (git add) نمی‌شود.

## ۴. قواعد Git/کامیت/PR مخصوص مخزن کد

[[META-CONV-001 — قواعد توسعه پروژه|META-CONV-001]] برای یک Vault مستندات Markdown/Obsidian نوشته شده است؛ نسخه تطبیق‌یافته آن برای یک مخزن کد نرم‌افزاری (`xennic-website`) به شرح زیر است:

| مورد | قاعده |
|---|---|
| شاخه‌ها | `main` (پایدار/قابل‌استقرار) ← `dev` (توسعه) ← `feature/<slug>` |
| کامیت مستقیم | هیچ کامیتی مستقیم روی `main`/`dev` مجاز نیست؛ همه تغییرات از طریق Pull Request |
| تأیید PR | چون توسعه‌دهنده واحد است، ساخت PR و Merge آن توسط همان عامل مجاز است؛ اما بدنه PR باید شامل What/Why/Checklist باشد |
| پیام کامیت | انگلیسی، الگوی Conventional Commits: `type(scope): description` (`feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `style`) |
| زبان محتوا | رابط‌کاربری و محتوای صفحات: فارسی (RTL)، دقیقاً طبق [[L2-MKT-004 — محتوای صفحات نسخه نخست وب‌سایت|L2-MKT-004]]؛ کد، کامنت، نام فایل/متغیر: انگلیسی |
| فایل‌های حساس | `.env`, `node_modules`, `.next`, کلیدها و اسرار هرگز commit نمی‌شوند؛ `.env.example` بدون مقدار واقعی از همان کامیت اول وجود دارد |

## ۵. قواعد انضباط دامنه (Scope Discipline)

- محدوده فاز ۱ دقیقاً همان چیزی است که در بخش ۱۹ [[L2-MKT-002 — طرح اجرایی و معماری وب‌سایت حرفه‌ای Xennic|L2-MKT-002]] تصویب شده است: هیچ فروشگاه، درگاه پرداخت، پنل کاربری پیچیده یا قابلیت پلتفرم در همین مرحله ساخته نمی‌شود.
- ساخت جدول/Schema مشترک `Customers` (طبق [[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]] بند ۴) به‌معنای ساخت رابط کاربری ورود/ثبت‌نام **نیست**؛ این جدول بدون رابط عمومی باقی می‌ماند.
- هیچ ادعای تخصصی، تجاری یا محتوای تازه اختراع نمی‌شود؛ تنها متن تأییدشده [[L2-MKT-004 — محتوای صفحات نسخه نخست وب‌سایت|L2-MKT-004]] منتشر می‌شود.
- هر تصمیم فنی/معماری که در مستندات مرجع به‌صراحت نیامده (انتخاب کتابخانه جدید، تغییر ساختار پوشه‌ها، تصمیم بزرگ UX) باید از مالک پرسیده شود؛ حدس زدن مجاز نیست.

> [!important] درس مستقیم از ممیزی مخزن قدیمی
> طبق [[META-INT-150 — یکپارچه‌سازی معماری وب‌سایت و پلتفرم Xennic|META-INT-150]] بند ۸، علت اصلی شکست تلاش قبلی (`feerozmandiha/xennic`)، بیش‌مهندسی و معماری Enterprise نامتناسب با یک شرکت تازه‌کار تک‌بنیان‌گذار بود. سادگی، دقت و تطابق کامل با مستندات مصوب — نه خلاقیت معماری مستقل — اولویت این پروژه است.

## ۶. پشته فناوری الزامی

خلاصه از [[L2-MKT-005 — معماری فنی و CMS نهایی وب‌سایت Xennic|L2-MKT-005]] (برای جزئیات کامل، همان سند باید خوانده شود):

| لایه | فناوری |
|---|---|
| Frontend | Next.js (App Router) + TypeScript + Tailwind CSS |
| CMS | Payload CMS، تعبیه‌شده در همان پروژه Next.js (نه سرویس جدا) |
| پایگاه‌داده | PostgreSQL ۱۶ — یک نمونه، Schema جدا به‌ازای هر دامنه (`website` اکنون؛ `platform`/`shop`/`consulting` در آینده) |
| فرم‌ها | Server Actions/Route Handler + Zod + honeypot |
| تحلیل رفتار | Umami (خوداستقرار) |
| میزبانی هدف (آینده) | همان VPS فعلی، پشت Caddy — فعلاً فقط توسعه محلی (بند ۸) |

## ۸. وضعیت استقرار (VPS) و زمان‌بندی

طبق [[META-INT-140 — نقشه مهاجرت زیرساخت اتوماسیون به سرور اختصاصی (VPS)|META-INT-140]] و بخش ۴ `L2-MKT-005`، استقرار واقعی روی VPS هنوز نباید آغاز شود؛ فاز ۰/A زیرساخت هنوز تکمیل نشده است. نشست توسعه فقط باید محیط **توسعه محلی** (Local Dev + Docker Compose) را راه‌اندازی کند و منتظر اطلاع‌رسانی جداگانه برای شروع استقرار واقعی بماند.

## ۹. فرآیند تعامل و گزارش‌دهی به کاربر

چون نشست توسعه از این Vault کاملاً جداست و هیچ اطلاع زنده‌ای از آن ندارد، عامل توسعه موظف است:
- پس از مطالعه کامل بند ۳، یک خلاصه یک‌پاراگرافی از درک خود از معماری، محدوده فاز ۱ و پشته فناوری ارائه دهد و **پیش از ساخت هر فایل کد، تأیید مالک را بگیرد**.
- در پایان هر مرحله مهم (اتمام Scaffold، اتمام یک صفحه، تکمیل CMS Collections)، یک خلاصه کوتاه از کار انجام‌شده و هر تصمیم جدید (در صورت وجود) ارائه دهد تا مالک بتواند در یک نشست بعدیِ این Vault، آن تصمیم را رسماً ثبت کند.
- در برابر هر ابهام یا تناقض در مستندات مرجع، فرض نسازد؛ از مالک بپرسد.

## ۲. قواعد غیرقابل‌مذاکره برای این مخزن کد
(چون META-CONV-001 برای مستندات Markdown نوشته شده، این نسخه تطبیق‌یافته برای کد است)

- Git Flow: main (پایدار/قابل‌استقرار) ← dev (توسعه) ← feature/<topic>-slug. هیچ کامیت مستقیمی
  روی main/dev مجاز نیست؛ همه تغییرات از طریق Pull Request. چون توسعه‌دهنده واحد هستی، می‌توانی PR
  بسازی و خودت Merge کنی — اما PR و توضیحات آن (What/Why/Checklist) اجباری است.
- Commit message: انگلیسی، الگوی Conventional Commits: type(scope): description
  (feat, fix, docs, chore, refactor, test, style). مثال: feat(payload): add Service and Page collections
- زبان رابط‌کاربری و محتوای صفحات: فارسی (RTL) طبق L2-MKT-004؛ کد، کامنت، نام فایل/متغیر: انگلیسی.
- هیچ ادعای تخصصی/تجاری جدید یا محتوای اختراعی منتشر نشود — فقط متن تأییدشده L2-MKT-004.
