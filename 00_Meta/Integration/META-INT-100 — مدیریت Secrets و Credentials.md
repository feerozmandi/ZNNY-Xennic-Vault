## ۱. هدف (Why)

تعیین سیاست یکتا برای ذخیره‌سازی، دسترسی و چرخش (Rotation) کلیدهای API، توکن‌های OAuth و Credentialهای زیرساخت اتوماسیون (n8n، Hermes، Qdrant، Open Notebook، GitHub) — موضوعی که در سیاست کلی امنیت اطلاعات شرکت ([[L2-SEC-001 — امنیت اطلاعات|L2-SEC-001]]) در سطح عملیاتی پوشش داده نشده است.

این نود، تفصیل عملیاتی اصل «Auditability» و «Human-in-the-loop» از [[META-INT-080 — معماری کلان سیستم‌عامل هوشمند سازمانی Xennic|META-INT-080]] (بند ۲.۳) برای زیرساخت فنی فعلی است.

---

## ۲. چرا این نود لازم شد

در بررسی نودهای فنی موجود، این موارد Secret/Credential بدون سیاست مشخص یافت شد:

- کلید API سرویس `gapgpt.app` (استفاده‌شده در [[META-INT-010 — RAG Obsidian → Qdrant — تکمیل|META-INT-010]]، بایگانی‌شده)
- توکن OAuth 2.1 بین Hermes و n8n (طبق [[META-INT-033 — ادغام Hermes با MCP n8n-official|META-INT-033]])
- دسترسی API به Qdrant (`http://localhost:6333`) و سرویس Embedding محلی TEI (`http://localhost:8001`)
- دسترسی API به Open Notebook (`http://localhost:5055`)
- پیکربندی Hermes در `config.yaml` که شامل اطلاعات Provider مدل است

هیچ‌کدام در مستندات موجود مشخص نمی‌کند این موارد **کجا ذخیره می‌شوند** (در n8n Credentials، در فایل محلی، در متغیر محیطی؟)، **چه کسی** به آن‌ها دسترسی دارد، و **چه زمانی** باید تعویض شوند. از آنجا که تمام این سرویس‌ها فعلاً روی یک کامپیوتر شخصی اجرا می‌شوند (طبق META-INT-050 و META-INT-070)، ریسک قرار گرفتن این Secretها در فایل‌های محلی بدون رمزنگاری بالاست.

> [!success] به‌روزرسانی ۱۴۰۵-۰۷-۳۰ — فهرست واقعی Credentialهای n8n استخراج شد
> با اجرای `docker exec xennic-n8n n8n export:credentials --all` (بدون `--decrypted` — طبق سیاست این نود، مقدار رمزگذاری‌شده Secretها هرگز بازیابی یا در Vault نوشته نمی‌شود)، فهرست کامل و واقعی ۹ Credential ثبت‌شده در n8n استخراج شد. جدول بخش ۳ اکنون شامل این داده واقعی است. **همچنین یک تصحیح مهم:** بررسی مستقیم API سرویس Open Notebook نشان داد که برخلاف فرض اولیه، این سرویس **بدون Auth نیست** — یک Header Auth واقعی (`Header Auth account` در n8n) برای تمام تماس‌ها با آن الزامی است.

## ۳. فهرست Secretهای شناخته‌شده

> [!warning] این جدول صرفاً شناسایی می‌کند، مقدار واقعی هیچ Secret را افشا نمی‌کند
> طبق سیاست، مقدار هیچ کلید/توکنی نباید در Git یا در این Vault نوشته شود — فقط **نام**، **نوع** و **کاربرد** Credential.

## ۵. سطح دسترسی

به‌جای این‌که همه Secretها در دسترس یک حساب باشند، دسترسی باید بر اساس نقش تعریف شود — منطبق با رجیستری عامل‌ها در META-INT-080 (بند ۶):

| نقش | دسترسی مجاز |
|---|---|
| مدیرعامل (مالک انسانی) | دسترسی کامل به همه Secretها |
| Hermes Agent | فقط توکن‌های لازم برای ابزارهای مجاز خودش (MCP obsidian، MCP n8n) |
| n8n Workflow | فقط Credential مشخص‌شده در همان Workflow، نه دسترسی سراسری |
| عامل‌های آینده (فروش، بازاریابی، ...) | هیچ دسترسی مستقیم به Secretهای زیرساختی؛ فقط از طریق API داخلی با سطح اختیار محدود (L0–L2 طبق Authority Matrix) |

### ۶.۱ رویداد چرخش کامل Credentialهای زیرساخت VPS — ۱۴۰۵-۰۸ (v0.3.0)

> [!warning] محرک: نشت تصادفی دو Secret در یک گفتگوی تشخیصی
> در جریان کار عملیاتی روی VPS، مقدار واقعی دو Secret (`INFRA_BACKUP_ENC_KEY` و `QDRANT_API_KEY`) به‌صورت تصادفی در یک گفتگوی تشخیصی چاپ شد. طبق رویهٔ بخش ۷ («پاسخ به نشت احتمالی»)، نه‌تنها همین دو مورد، بلکه به‌عنوان یک اقدام احتیاطی، **تمام ۸ Secret/Credential شناخته‌شدهٔ زیرساخت خودمیزبانی VPS** (n8n + SurrealDB/Open Notebook + Qdrant + Postgres + Bale) در یک دوره بررسی و چرخانده شدند. این رویداد همچنین باعث شد قاعدهٔ جدیدی برای این سند تثبیت شود: **هیچ خروجی خام دستوری که می‌تواند حاوی مقدار واقعی یک Secret باشد، نباید در کانال‌های گفتگویی پیست شود** — فقط خروجی Redact‌شده (`sed 's/=.*/=<hidden>/'`) یا تأییدهای ساده موفق/ناموفق/تعداد مجاز است؛ برای دیدن مقدار واقعی یک Secret (مثلاً برای Paste در فیلد یک Credential n8n)، باید مستقیماً فایل مربوطه در ویرایشگر (VS Code روی VPS) باز شود، نه در گفتگو.

| # | Secret/Credential | چرا چرخانده شد | روش تعویض | روش تأیید نهایی |
|---|---|---|---|---|
| ۱ | `INFRA_BACKUP_ENC_KEY` | نشت مستقیم در گفتگو (محرک اصلی رویداد) | `openssl rand -hex 32` جدید در `.env`؛ دو بار چرخانده شد (چرخش اول هم به‌اشتباه در گفتگو افشا شد و بلافاصله چرخش دوم انجام شد) | رمزگشایی موفق یک Dump تست با کلید جدید |
| ۲ | `POSTGRES_PASSWORD` | اقدام احتیاطی هم‌زمان با رویداد نشت | تغییر پسورد کاربر Postgres + به‌روزرسانی `.env` و Credential n8n | اجرای سالم n8n بعد از `docker compose up -d` (بعد از رفع یک حادثهٔ جانبی آلودگی Shell ناشی از `source .env`) |
| ۳ | `SURREAL_PASSWORD` | اقدام احتیاطی | **تلاش اول به‌اشتباه موفق تلقی شد** (`DEFINE USER` ساده روی کاربری که از قبل وجود داشت، فقط خطای «already exists» با HTTP 200 برگرداند — نه تغییر واقعی)؛ با تست مستقیم HTTP (پسورد `.env` → 401) کشف و با `DEFINE USER OVERWRITE root ... PASSWORD ...` واقعاً اصلاح شد | تست مستقیم HTTP دوباره قبل و بعد از اعمال (کد وضعیت، نه فقط گزارش کاربر) + تست end-to-end `[OPS-01]`/`[RAG-02]` |
| ۴ | `OPEN_NOTEBOOK_PASSWORD` | اقدام احتیاطی | مقدار جدید در `.env` + Credentialهای «Header Auth» مرتبط در n8n | ورود موفق UI + اجرای موفق `[KNW-02]`/`[RAG-02]` (بعد از رفع یک باگ جداگانه: افتادن پیشوند `Bearer ` در Credential) |
| ۵ | `OPEN_NOTEBOOK_ENCRYPTION_KEY` | اقدام احتیاطی | مقدار جدید در `.env`؛ تأیید شد که هیچ کلید API ارائه‌دهندهٔ هوش مصنوعی از طریق تنظیمات Open Notebook ذخیره نشده بود (ریسک غیرقابل‌بازیابی‌شدن داده، منتفی) | راه‌اندازی سالم `open_notebook` |
| ۶ | `QDRANT_API_KEY` | نشت مستقیم در گفتگو (محرک اصلی رویداد) | مقدار جدید در `.env` + Credential مرتبط در n8n | اجرای موفق گرهٔ Qdrant در `[RAG-02]` |
| ۷ | توکن ربات Bale | اقدام احتیاطی | صدور توکن جدید از BotFather بله + به‌روزرسانی Credential `BaleMessenger account` در n8n | دریافت موفق پیام تست در کانال |
| ۸ | `N8N_ENCRYPTION_KEY` | اقدام احتیاطی | رویهٔ رسمی ۵مرحله‌ای n8n: Export رمزگشایی‌شدهٔ همهٔ Credentialها → حذف `~/.n8n/config` (کَش کلید قدیمی) → تنظیم کلید جدید + Restart تمیز (بدون خطای «Mismatching encryption keys») → Import مجدد → پاک‌سازی امن هر دو نسخهٔ رمزگشایی‌شده (treat as toxic waste). یک بار در میانهٔ کار به‌دلیل حذف زودهنگام فایل Export (قبل از تکمیل `docker cp`) یک رویداد از‌دست‌رفتن موقت Credentialها رخ داد که با بازگردانی از `.env.bak` کاملاً جبران شد؛ رویهٔ تکرار شده با تأیید گام‌به‌گام هر مرحله | پیام «Successfully imported ۷ credentials» + تأیید بصری مقدار پر در فیلد پسورد Credential «SurrealDB Root» از طریق UI n8n |

**درس‌های کلیدی این رویداد (برای هر چرخش آیندهٔ مشابه):**

1. **تأیید یک کاربر («انجام شد») برای یک مرحلهٔ چرخش Secret کافی نیست** — اگر موفقیت آن مرحله فقط از طریق یک کد وضعیت HTTP یا پیام صریح یک API قابل تشخیص است، آن خروجی دقیق باید دیده و بررسی شود، نه خلاصهٔ کلامی کاربر. (مورد `SURREAL_PASSWORD` نمونهٔ مستقیم همین مشکل بود.)
2. برای عملیات مخرب/برگشت‌ناپذیر (مثل حذف تنها نسخهٔ رمزگشایی‌شدهٔ یک Backup از Credentialها)، دستورها باید **یکی‌یکی و با تأیید خروجی هر مرحله** اجرا شوند، نه در یک بلوک چندخطی.
3. هرگز از `set -a; source .env; set +a` در یک Shell تعاملی استفاده نشود — مقادیر قدیمی Export‌شده در همان نشست باقی می‌مانند و روی مقدار جدید `.env` در فراخوانی‌های بعدی `docker compose up` اولویت می‌گیرند.
4. مقدار واقعی هیچ Secret نباید در کانال گفتگویی دیده شود؛ همیشه از خروجی Redact‌شده یا بررسی مستقیم در ویرایشگر (VS Code روی VPS) استفاده شود.
5. بعد از اتمام یک چرخهٔ چرخش، باید یک **رگرسیون End-to-End واقعی** (نه فقط یک نود مجزا) روی همهٔ Workflowهای مصرف‌کنندهٔ آن Secretها اجرا شود — همین رگرسیون در این رویداد دو باگ کاملاً مستقل و غیرمرتبط با خودِ چرخش را هم آشکار کرد (مستندشده در [[META-INT-110 — زیرساخت به‌صورت کد و بازیابی پس از خرابی|META-INT-110]]، بخش ۷.۷، یافته‌های ۱۳ و ۱۴).

## ۷. پاسخ به نشت احتمالی

۱. **توقف فوری** Workflow یا Agent مرتبط.
۲. **ابطال (Revoke)** Secret نشت‌یافته در سرویس مبدأ.
۳. **صدور Secret جدید** و به‌روزرسانی محل ذخیره رسمی.
۴. **ثبت رخداد** طبق رویه پاسخ به حادثه در [[L2-SEC-001 — امنیت اطلاعات|L2-SEC-001]].
۵. **بازبینی** این‌که آیا Secret دیگری هم در همان کانال نشت در معرض خطر بوده است.

## ۱۱. Changelog

- **v0.3.0 (۱۴۰۵-۰۸-۰۷):** افزودن بخش ۶.۱ — مستندسازی کامل رویداد چرخش هر ۸ Secret/Credential زیرساخت خودمیزبانی VPS (n8n، SurrealDB/Open Notebook، Qdrant، Postgres، Bale) که با نشت تصادفی دو Secret در یک گفتگوی تشخیصی آغاز شد. ثبت روش دقیق تعویض و تأیید هرکدام، و پنج درسِ کلیدی عملیاتی (مهم‌ترین‌شان: تأیید کلامی کاربر برای موفقیت یک چرخش Secret کافی نیست، باید خروجی واقعی HTTP/CLI دیده شود — که دقیقاً همین نکته باعث کشف یک چرخش ناقص در `SURREAL_PASSWORD` شد که قبلاً به‌اشتباه «انجام‌شده» گزارش شده بود). دو مورد اقدام جدید اضافه شد (ادغام کردنشیال‌های تکراری Header Auth، فیلتر فهرست کامل Credentialها پیش از هر چرخش آینده)؛ یک اقدام قدیمی (تعیین تاریخ شروع چرخه Rotation) برای Secretهای VPS بسته شد.
- **v0.2.1 (۱۴۰۵-۰۸-۰۱):** رفع اشکال رندر جدول — Escape کردن `|` داخل یک لینک Wiki در جدول بخش ۴ که باعث شکستن ستون‌بندی جدول در رندررهای استاندارد Markdown (از جمله GitHub) می‌شد؛ بدون تغییر محتوایی.
- **v0.2.0 (۱۴۰۵-۰۷-۳۰):** تکمیل جدول Credentialها با داده واقعی استخراج‌شده از `docker exec xennic-n8n n8n export:credentials --all` (۹ مورد، بدون افشای مقدار رمزگذاری‌شده)؛ تصحیح فرض نادرست «Open Notebook بدون Auth است» (واقعاً `Header Auth account` دارد)؛ شناسایی تکرار دو Credential Qdrant؛ شناسایی Credential ناشناخته `APITemplate.io account`؛ ثبت یادآوری حیاتی درباره Rotation کلید Local REST API و گواهی‌های RSA/CA Obsidian که قبلاً به‌صورت متن ساده مشاهده شدند؛ تغییر وضعیت به `review`.
- **v0.1.0 (۱۴۰۵-۰۷-۳۰):** ایجاد اولیه در پی ممیزی کامل پوشه `00_Meta/Integration` — مستندسازی شکاف «عدم وجود سیاست مدیریت Secrets برای زیرساخت اتوماسیون».
