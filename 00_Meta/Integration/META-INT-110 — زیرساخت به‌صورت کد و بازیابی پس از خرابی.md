## ۱. هدف (Why)

مستندسازی وضعیت فعلی زیرساخت اتوماسیون (n8n، Qdrant، TEI Embedding، Open Notebook) و تعریف مسیر رسیدن به **زیرساخت بازتولیدپذیر** (Infrastructure as Code) به‌جای وابستگی کامل به پیکربندی دستی روی یک کامپیوتر شخصی.

این نود خروجی مستقیم فاز ۰ («شناخت اتصال واقعی چهار ابزار، نسخه‌ها، دسترسی‌ها ... و نقاط شکست») در [[META-INT-080 — معماری کلان سیستم‌عامل هوشمند سازمانی Xennic|META-INT-080]] (بند ۱۱) است.

---

## ۲. وضعیت فعلی (As-Is)

بر اساس [[META-INT-050 — راه‌اندازی کامل Hermes|META-INT-050]] و [[META-INT-070 — نقشه Open Notebook برای n8n و Hermes|META-INT-070]]، زیرساخت فعلی چنین است:

| سرویس | نسخه | محل اجرا | نحوه نصب |
|---|---|---|---|
| n8n | v2.42.6 | یک کامپیوتر Windows (Local) | نامشخص (احتمالاً نصب مستقیم Node.js یا Docker — تأیید نشده) |
| Qdrant | v1.18.3 | همان کامپیوتر، `localhost:6333` | Docker (طبق META-INT-020) |
| TEI (Text Embeddings Inference) | v1.9.4 | همان کامپیوتر، `localhost:8001` | Docker |
| Open Notebook | v1.15.0 | همان کامپیوتر، `localhost:5055` | نامشخص |
| Hermes Desktop App | نامشخص | همان کامپیوتر (Windows، کاربر Narges) | نصب دستی برنامه Desktop |
| Obsidian Vault (این مخزن) | — | همان کامپیوتر + GitHub | Git (تنها بخشی که واقعاً نسخه‌بندی و Backup خودکار دارد) |

**نتیجه**: از ۶ مؤلفه اصلی، فقط Obsidian Vault واقعاً در کنترل نسخه و قابل بازسازی خودکار است. بقیه به‌صورت دستی روی یک دستگاه پیکربندی شده‌اند.

---

## ۳. ریسک تک‌نقطه‌ای بودن (Single Point of Failure)

> [!danger] ریسک اصلی
> اگر این یک کامپیوتر خراب شود، دزدیده شود یا سیستم‌عامل آن نیاز به نصب مجدد پیدا کند، **تمام زیرساخت RAG، n8n و Open Notebook از بین می‌رود** و فقط محتوای متنی Obsidian (که در GitHub است) قابل بازیابی است. پیکربندی Qdrant Collection، Workflowهای n8n، و تنظیمات Open Notebook باید از صفر و از حافظه بازسازی شوند.

این دقیقاً همان ریسکی است که اصل «Auditability» و «Continuous Improvement» در META-INT-080 (بند ۲.۳) برای جلوگیری از آن طراحی شده‌اند، اما هنوز در لایه زیرساخت فنی پیاده نشده‌اند.

## ۴. دارایی‌هایی که باید در Git نسخه‌بندی شوند

| دارایی | وضعیت فعلی | وضعیت هدف |
|---|---|---|
| Workflowهای n8n (export JSON) | ❌ نسخه‌بندی نمی‌شوند | ✅ هر Workflow فعال به‌صورت JSON در پوشه‌ای مثل `infra/n8n-workflows/` Export و Commit شود |
| تنظیمات Docker (docker-compose) برای Qdrant/TEI/Open Notebook | ❌ وجود ندارد | ✅ `infra/docker-compose.yml` با نسخه‌های دقیق سرویس‌ها |
| اسکیمای Qdrant Collection (نام، ابعاد، Distance، Indexها) | ✅ در META-INT-020 مستند است (متن)، ❌ به‌صورت اسکریپت اجرایی نیست | ✅ اسکریپت ایجاد Collection (شبیه `generate_vault_index.py`) در `00_Meta/Scripts/` |
| نقشه Notebook IDs (`notebook_map.json`) | ✅ در META-INT-070 به‌صورت متن مستند است؛ فایل اصلی فقط محلی (`F:\ahmad\...`) است | ✅ خود فایل JSON هم در مخزن نگهداری شود (غیر از بخش Corporate که محرمانه است) |
| قالب `.env.example` (بدون مقدار واقعی) | ❌ وجود ندارد | ✅ لیست متغیرهای محیطی لازم بدون مقدار، برای بازسازی سریع |

## ۵. دارایی‌هایی که نباید در Git باشند

- هیچ Secret/Credential واقعی (طبق [[META-INT-100 — مدیریت Secrets و Credentials|META-INT-100]])
- محتوای Notebook `Corporate` (اسناد محرمانه شرکت — طبق META-INT-070)
- داده‌های واقعی Qdrant (Vectorها)، فقط اسکیمای ساخت Collection

## ۶. برنامه بازیابی پس از خرابی (DR)

| مرحله | اقدام | پیش‌نیاز |
|---|---|---|
| ۱ | بازسازی Docker Compose برای Qdrant + TEI + Open Notebook | وجود `infra/docker-compose.yml` در Git |
| ۲ | اجرای اسکریپت ساخت Collection در Qdrant با همان نام/ابعاد/Index | وجود اسکریپت نسخه‌بندی‌شده |
| ۳ | Import مجدد Workflowهای n8n از فایل‌های Export شده | وجود export JSON در Git |
| ۴ | بازسازی Credentialها از محل رسمی (نه از حافظه) | اجرای کامل META-INT-100 |
| ۵ | اجرای مجدد RAG-01/RAG-02 برای بازسازی ایندکس Qdrant از صفر | وجود [[META-INT-090 — رجیستری Workflowهای n8n|META-INT-090]] به‌روز |
| ۶ | تست جستجوی معنایی (مطابق تست‌های META-INT-034) برای تأیید صحت بازیابی | — |

> [!warning] وضعیت فعلی این برنامه
> این برنامه **هنوز هرگز تست نشده است**. تا زمانی‌که یک بازیابی آزمایشی کامل انجام نشود، نمی‌توان ادعا کرد سیستم واقعاً قابل بازیابی است.
