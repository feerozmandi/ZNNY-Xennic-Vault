## ۰. شروع سریع (روی خودِ سرور)

> [!warning] مهم
> این دستورها **روی VPS** اجرا می‌شوند، نه روی لپ‌تاپ.
> اگر همین حالا داخل سرور هستید (`xennic@server2085:~$`)، دستور `ssh` لازم نیست —
> از سرور به خودش SSH زدن با `Connection timed out` شکست می‌خورد.

```bash
# ۱) گرفتن فایل‌ها (مخزن عمومی است؛ نیازی به توکن نیست)
cd ~
git clone https://github.com/feerozmandi/ZNNY-Xennic-Vault.git
cd ZNNY-Xennic-Vault/iee1405-deploy

# ۲) بررسی پیش‌نیازها — در یک نگاه می‌گوید چه چیزی کم است
bash 03_ops/preflight.sh
```

> [!note] کشف خودکار محیط
> روی این سرور، هیچ‌کدام از پیش‌فرض‌های معمول درست نیستند و لازم نیست دستی تنظیم شوند:
> کانتینر `xennic-infra-postgres-1` · کاربر دیتابیس `n8n` (نه `postgres`) ·
> دیتابیس برنامه وجود ندارد و **در گام استقرار ساخته می‌شود** (`xennic`).
> دیتابیس `n8n` هیچ‌وقت دست نمی‌خورد.

`preflight.sh` نام واقعی کانتینرها، نام دیتابیس، نسخه n8n، وضعیت متغیرها و
فضای دیسک را بررسی می‌کند و در پایان **دستور بعدی را با مقادیر واقعی** چاپ می‌کند:

توکن بله در `.env` با کلید `BALE_TOKEN_BOT` نگه داشته می‌شود و `BALE_API_URL`
در فایل override از همان ساخته می‌شود — توکن در هیچ فایل مخزن یا JSON نیست.

```bash
bash 03_ops/setup_env.sh          # پر کردن BALE_TOKEN_BOT و متغیرهای لازم
bash 00_audit/audit_postgres.sh                                  # فقط خواندن
APP_PASSWORD="$(openssl rand -base64 18)" bash 03_ops/deploy_sql.sh  # ساختار + منطق
bash 03_ops/import_workflows.sh import     # فقط گردش‌کارها را وارد می‌کند
bash 03_ops/activate_all.sh                # کارت اعتبارنامه + انتشار + ری‌استارت + بررسی
bash 03_ops/smoke_test.sh                  # آزمون دود: توکن، گردش‌کارها، تازگی دریافت
```

> [!tip] اگر `preflight.sh` گفت «هیچ سرویس در حال اجرا نیست»
> این یعنی PostgreSQL واقعاً بالاست یا نه — نه اینکه اسکریپت اشتباه کرده باشد.
> `docker ps` را ببینید؛ اگر کانتینر `postgres` هست ولی `exited` است، لاگش را بخوانید:
> `docker logs --tail 30 <container>`. سپس `cd ~/xennic-infra && docker compose up -d`.

رمز ساخته‌شده در `~/.iee1405-app-password` ذخیره می‌شود تا کارت اعتبارنامه n8n را با آن بسازید.

> [!note] چرا دیگر `--branch` لازم نیست
> این بسته پیش‌تر فقط روی یک شاخهٔ کاری بود (PR #75). آن PR ادغام شد و پوشهٔ
> `iee1405-deploy` اکنون روی شاخهٔ `dev` هست، پس `git clone` ساده کافی است.
> اگر شاخهٔ کاری دیگری را دنبال می‌کنید، `--branch <نام>` بدهید.

## ۲. استقرار ساختار پایگاه‌داده

```bash
# نام دیتابیس فعلی سرویس postgres را تأیید کنید:
docker compose -f ~/xennic-infra/docker-compose.yml exec -T postgres psql -U postgres -l

# سپس (اگر نام دیتابیس xennic نیست، PG_DB را عوض کنید):
PG_DB=xennic APP_PASSWORD='<رمز-قوی>' bash 03_ops/deploy_sql.sh
```

چه چیزی ساخته می‌شود:

| فایل | محتوا |
|---|---|
| `01_schema_core.sql` | ۲ schema (`crm` دائمی + `iee1405` نمایشگاهی)، ۲۰+ جدول، enumها، تریگرها، ممیزی |
| `02_seed_reference.sql` | ۱۵ دسته محصول (همان کدهای فرم‌های PRJ-IEE-014)، رکورد نمایشگاه ۱۴۰۵، کاربران سرویس |
| `03_views.sql` | نماهای گزارش: کارت شرکت، وظایف باز، خلاصه روز، کیفیت داده، خروجی اکسل |
| `04_bot_logic.sql` | منطق کامل ربات + متن پیام‌ها در جدول `bot_messages` |
| `05_ops_helpers.sql` | offset، صف ارسال، یادآور، خلاصه، سلامت، تحویل تضمین‌شده |
| `06_roles.sql` | نقش `iee_app` (بدون DDL و بدون DELETE)، `iee_panel`، `iee_report` |
| `08_exhibitor_mirror.sql` | آینهٔ فقط‌خواندنی فهرست غرفه‌داران (`barghpa`) + کارت شرکت با **حوزهٔ فعالیت** |
| `10_interview.sql` | بانک سؤال مصاحبهٔ غرفه، جدول `iee1405.interviews`، سؤال اختصاصی هر شرکت |

| `09_company_list.sql` | فهرست دکمه‌ای دو‌ستونی شرکت‌ها، جست‌وجوی دکمه‌ای، کارت + دکمهٔ «🎤 مصاحبه در غرفه» |

همه فایل‌ها **idempotent** هستند: اجرای دوباره چیزی را خراب نمی‌کند.

> [!note] ترتیب اجرا
> `10_interview.sql` **پیش از** `09_company_list.sql` اجرا می‌شود، چون خودآزمون
> فایل ۰۹ وجود دکمهٔ «🎤 مصاحبه» (که از ۱۰ می‌آید) را می‌سنجد. این ترتیب در
> `deploy_sql.sh` ثابت است و روی پایگاه تازه آزموده شد.

### چرا منطق ربات در SQL است؟

چون می‌توان آن را **واقعاً آزمایش کرد** — کاری که در طراحی همین بسته انجام شد
(۲۴ آزمون سرتاسری روی PostgreSQL واقعی). مزیت‌های دیگر:

- n8n ساده می‌ماند (۹ گره) و خطای پیکربندی در آن کم می‌شود

## ۳. ایمپورت گردش‌کارهای n8n

### پیش‌نیاز: متغیرهای محیطی

```bash
cd ~/xennic-infra
cp /path/to/iee1405-deploy/03_ops/docker-compose.override.yml .

```

حداقل‌های لازم در `.env`:

```env
BALE_API_URL=https://tapi.bale.ai/bot<TOKEN>
N8N_BLOCK_ENV_ACCESS_IN_NODE=false
GENERIC_TIMEZONE=Asia/Tehran
```

### ایمپورت

```bash
bash 03_ops/import_workflows.sh import
bash 03_ops/import_workflows.sh list
```

چهار گردش‌کار:

| فایل | نام در n8n | زمان‌بندی | کار |
|---|---|---|---|
| `wf-01-bale-ingest.json` | IEE1405-01 — دریافت پیام‌های بله | هر ۵ ثانیه | getUpdates (long-poll ۴ ثانیه) → ثبت در PG → پاسخ |
| `wf-02-reminders.json` | IEE1405-02 — یادآور پیگیری‌ها | روزانه ۰۷:۳۰ | پیگیری‌های سررسید تا ۳ روز |
| `wf-03-digest.json` | IEE1405-03 — خلاصه پایان روز | روزانه ۲۰:۳۰ | آمار روز + نزدیک‌ترین پیگیری‌ها |
| `wf-04-health.json` | IEE1405-04 — پایش سلامت | هر ۳۰ دقیقه | فقط وقتی مشکل هست هشدار می‌دهد |

> [!danger] خطای کشنده‌ای که واقعاً رخ داد: نام متغیر محیطی
> گردش‌کارها آدرس بله را از `$env.BALE_API_URL` می‌خوانند — همین متغیری که
> `setup_env.sh` می‌سازد و `preflight.sh` تأیید می‌کند. اگر روزی کسی آن را به
> نام دیگری (مثل `BALE_BOT_TOKEN`) تغییر دهد، آدرس به `…/botundefined/…`
> تبدیل می‌شود: گره HTTP نه خطای روشن می‌دهد و نه پیام می‌فرستد، فقط اجراها
> در حالت `running` گیر می‌کنند. `validate_workflows.py` از این پس این را
> **خطا** می‌گیرد، نه هشدار.

> [!important] هر گره HTTP باید `timeout` داشته باشد
> بدون `options.timeout` درخواست معلق تا ۵ دقیقه باز می‌ماند، صف اجراها پر
> می‌شود و `last_poll_at` هرگز تازه نمی‌شود. مقدار این نسخه: ۵ ثانیه.
> بازفرست خودکار لازم نیست: پاسخ‌ها در دیتابیس می‌مانند و اجرای بعدی
> (هر ۵ ثانیه) دوباره تلاش می‌کند.

### اتصال اعتبارنامه + فعال‌سازی (یک دستور)

در n8n 2.x دستور `update:workflow --active=true` منسوخ شده و کار نمی‌کند؛
راه درست `publish:workflow` است و **بعد از انتشار باید n8n ری‌استارت شود**،
وگرنه تغییرات اعمال نمی‌شوند. `activate_all.sh` همین‌ها را انجام می‌دهد:

0. میزبان دیتابیس را با **اتصال TCP واقعی از داخل کانتینر n8n** پیدا می‌کند
   (`postgres`، نام سرویس compose یا نام کانتینر) — به‌جای حدس‌زدن
1. کارت اعتبارنامه `Xennic PostgreSQL` (شناسه `XENNIC-PG-CREDENTIAL`) را با
   همان میزبان و رمز `~/.iee1405-app-password` می‌سازد
2. هر چهار گردش‌کار `IEE1405*` را منتشر می‌کند
3. `docker compose restart n8n` و انتظار تا بالا آمدن
4. تعداد گردش‌کارهای فعال و تازگی `last_poll_at` را بررسی می‌کند

```bash
bash 03_ops/activate_all.sh
```

خروجی موفق:

```
[ OK ] اعتبارنامه XENNIC-PG-CREDENTIAL
[ OK ] انتشار: 4 گردش‌کار
[ OK ] فعال: 4 از 4
[ OK ] دریافت پیام‌ها فعال است (last_poll_at تازه شد)
```

> [!important] اگر «فعال: 0 از 4» دیدید
> یعنی `publish` انجام شده ولی n8n ری‌استارت نشده، یا متغیر
> `N8N_RUNNERS_ENABLED`/`N8N_BLOCK_ENV_ACCESS_IN_NODE` در `.env` مانع شده است.
> `docker compose restart n8n` را دستی بزنید و دوباره اسکریپت را اجرا کنید.

## ۳.۵.۲. کار در رابط n8n (گام‌به‌گام، نود به نود)

### بازکردن UI

n8n فقط روی `127.0.0.1` سرور گوش می‌دهد (قاعده امنیتی). پس با تونل SSH بازش کنید:

```bash
bash 03_ops/open_ui.sh
```

اسکریپت، آدرس و پورت SSH را از متغیر `SSH_CONNECTION` جلسه شما می‌خواند و یک
دستور **آماده کپی** چاپ می‌کند؛ همان را روی لپ‌تاپ خودتان اجرا کنید و بعد
`http://localhost:5678` را باز کنید.

### مسیر بررسی

| گام | کار در UI | نتیجه سالم | اگر خراب بود یعنی |
|---|---|---|---|
| ۱ | Workflows → `IEE1405-01` | چهار گردش‌کار دیده می‌شوند | ایمپورت انجام نشده |
| ۲ | گره `📍 خواندن offset` → **Execute step** | یک ردیف `offset = 0` | اعتبارنامه PostgreSQL یا دسترسی `iee_app` |
| ۳ | گره `💓 ضربان دریافت` → **Execute step** | یک `timestamp` برمی‌گردد | تابع `poll_heartbeat` ساخته نشده (`deploy_sql.sh`) |
| ۴ | گره `📥 دریافت پیام‌ها` → **Execute step** | پاسخ `ok:true` | **همین‌جا موضوع را پیدا می‌کنیم** |
| ۵ | گره `🩺 بازرسی پاسخ بله` | پاسخ عیناً برمی‌گردد | تابع `poll_watch` نیست |
| ۶ | گره `💬 ارسال پاسخ` → **Execute step** | `message_id` برمی‌گردد | پارامترهای `chat_id`/`text_body` |

> [!tip] «Execute step» دقیقاً همان چیزی است که لازم داریم
> هر گره را می‌توان جدا اجرا کرد؛ پنل پایین صفحه خروجی و متن خطا را نشان می‌دهد.
> با این کار لازم نیست منتظر زمان‌بند بمانیم.

## ۴.۵. اتصال ربات به فهرست نمایشگاه (آینهٔ `barghpa`)

```
۲۹۷/۷۰۰/۳۰۰                                       آینهٔ فقط‌خواندنی        (n8n بی‌تغییر)
```

### اجرا (دو دستور)


`load_exhibitors.sh` این کارها را می‌کند: از پایگاه SQLite یک فایل SQL می‌سازد،

می‌کند و در پایان با `barghpa.selftest()` عددها را تطبیق می‌دهد.

### دستورهای ربات

| در بله | نتیجه |
|---|---|
| `/c` | خلاصهٔ آینه: ۲۹۷ شرکت، ۷۰۰ تماس، سطح اطمینان، زمان آخرین بارگذاری |
| `/c ایران ترانسفو` | جست‌وجو (ي/ك عربی، نیم‌فاصله، ارقام فارسی هم پیدا می‌شود) |

| دکمه‌های «◀ قبل / بعد ▶» و فهرست | **همان پیام ویرایش می‌شود**، پیام تازه ساخته نمی‌شود |
| شرکت‌های ثبت‌شده با `/new` | بالای صفحهٔ اول فهرست با «🆕» و دکمهٔ دم‌دست؛ در جست‌وجو هم پیدا می‌شوند |

برای دستورهای متنی هیچ تغییری در n8n لازم نیست: گردش‌کار `wf-01` کل آپدیت را به
`iee1405.bot_dispatch_json()` می‌دهد و دستور تازه همان‌جا پاسخ می‌گیرد.
**استثنا — ویرایش پیام:** از v0.1.40 به بعد `wf-01` سه گره تازه دارد
(`🔀 روش ارسال` · `✏️ ویرایش پیام` با `editMessageText` · `🔀 بررسی ویرایش`) تا
دکمه‌های قبل/بعد همان پیام را ویرایش کنند؛ پس یک بار ایمپورت دوباره لازم است:

```bash
bash 03_ops/import_workflows.sh import
bash 03_ops/activate_all.sh
```

اگر این گره‌ها نباشند، فهرست و کارت **باز هم کار می‌کنند** — فقط هر بار پیام تازه
می‌آید (رفتار نسخهٔ ۰.۱.۳۹).

### کارت چه می‌گوید و چه نمی‌گوید

```
🏭 توسعه پست‌های ایران ترانسفو
🏷 حوزه فعالیت: تولید پست و تابلو فشار متوسط
سالن: فضای باز | غرفه: ثبت‌نشده
شناسه: 1
منبع: سایت رسمی (ادعای منبع)
✅ وندور لیست توانیر
🎯 در فهرست پایلوت: رتبه 1
```

«حوزه فعالیت» از ستون «نوع فعالیت» همان فایل اکسل می‌آید و **زیر نام** چاپ
می‌شود؛ اگر در فایل خالی باشد، همان‌جا نوشته می‌شود «ثبت‌نشده (با به‌روزرسانی
داده پر می‌شود)» — چیزی حدس زده نمی‌شود.

- شماره‌های تماس در مخزن عمومی **نمی‌آیند**؛ نمونهٔ بالا عمداً بی‌شماره است
  (در پایگاه واقعی، تماس‌ها با سطح اطمینان رسمی/حدسی چاپ می‌شوند).
- اگر هیچ تماس رسمی نبود: «⚠️ تماس‌ها تأییدنشده‌اند … پیش از هر پیشنهاد تأیید کنید.»
- اگر هیچ تماسی نبود: «⚠️ هیچ تماسی ثبت نشده» + پیوند جست‌وجوی دستی.
- **غرفه ساخته نمی‌شود:** منبع شمارهٔ غرفه ندارد، پس «ثبت‌نشده» می‌ماند.

### سه چیز که آینه نمی‌کند

1. هیچ ردیفی در `crm.organizations` نمی‌نویسد (تصمیم R5).
2. هیچ درخواست شبکه‌ای نمی‌زند و چیزی را «تأییدشده» نمی‌کند.
3. تعامل‌های میدانی را نمی‌نویسد؛ ثبت سر میز همچنان در ابزار SQLite است.

پاک‌کردن کامل و بی‌اثر: `DROP SCHEMA barghpa CASCADE;` (در آزمون: ۱۵ شیء پاک و
CRM دست‌نخورده).

### شرکت تازه‌ای که با `/new` ثبت می‌کنید کجاست؟

دو منبع داریم و این دو عمداً جدا هستند:

| منبع | چه چیزی | چه کسی می‌نویسد |
|---|---|---|
| آینهٔ `barghpa` | **کاتالوگ نمایشگاه** (۲۹۷ شرکت از فایل برق‌پا) | فقط `load_exhibitors.sh` — ربات هرگز در آن نمی‌نویسد |
| `crm.organizations` | **شرکت‌های ثبت‌شده با ربات** (`/new`) و CRM | خودِ ربات |

تا نسخهٔ ۰.۱.۴۱ فهرست و جست‌وجو فقط آینه را می‌دیدند؛ یعنی شرکتی که با `/new`
ثبت می‌شد در CRM بود ولی در «لیست شرکت‌ها» دیده نمی‌شد. از **۰.۱.۴۲** هر دو
منبع با هم نشان داده می‌شوند:

- **صفحهٔ اول فهرست**، بالای متن: «🆕 ثبت‌شده در ربات (۳):» با ردیف دکمه‌های
  خودش (`callback_data: o:<ORG-code>`) و پیش از ردیف ناوبری. صفحه‌های بعدی
  دست‌نخورده‌اند.
- **جست‌وجو** (تایپ نام، یا «🔎 جست‌وجو»/`/search`): اگر در آینه نبود، در
  شرکت‌های ثبت‌شده هم می‌گردد. اگر فقط در CRM بود، همان‌جا کارت‌اش با یک ضربه
  باز می‌شود.
- **کارت CRM** با دکمهٔ `o:` می‌آید (همان کارت `/org`)، با «↩ بازگشت به فهرست»
  و «🔎 جست‌وجوی دیگر»؛ و مثل بقیهٔ دکمه‌ها **همان پیام را ویرایش می‌کند**.

> [!note] چه شرکتی «ثبت‌شده در ربات» حساب می‌شود
> هر شرکتی در CRM که یا برای نمایشگاه ۱۴۰۵ مشارکت دارد (مرحلهٔ غرفهٔ `/new`)،
> یا با `/new` ساخته شده و جریانش نیمه‌کاره مانده است. شرکتی که نامش در آینه هم
> هست **دوبار نشان داده نمی‌شود** — همان ردیف کاتالوگ برنده است.
>
> این کار به تصمیم R5 دست نمی‌زند: آینه همچنان فقط‌خواندنی است و ربات هیچ
> ردیفی در آن نمی‌نویسد؛ فقط **نمایش** دو منبع یکی شده است.

### مصاحبه در غرفه (دکمهٔ «🎤 مصاحبه در غرفه»)

هدف: در همان چند دقیقهٔ ایستادن سرِ غرفه، چیزی ثبت شود که در فهرست نیست —
**به نام و سمت خودِ مصاحبه‌شونده**، تا بعداً معلوم باشد چه کسی چه گفته است.

روی کارت هر شرکت، بالاتر از ردیف بازگشت، یک ردیف جداگانه هست:

```
🎤 مصاحبه در غرفه        ← callback_data: i:<company_id>
```

مسیر گفت‌وگو (همه در **همان پیام**، با ویرایش — پیام تازه ساخته نمی‌شود):

| گام | چه می‌پرسد | وضعیت نشست |
|---|---|---|
| ۱ | «نام مصاحبه‌شونده؟» | `iv_name` |
| ۲ | «سمت ایشان در شرکت؟» | `iv_role` |
| ۳ | شش سؤال پیش‌فرض، یکی‌یکی | `iv_q` |
| ۴ | جمع‌بندی و ثبت | `idle` |

در هر گام دو راه خروج هست: «⏭ رد کردن» (`x:s`) سؤال فعلی را بی‌پاسخ رد می‌کند و
«✖ پایان زودهنگام» (`x:e`) همان‌جا مصاحبه را **نیمه‌کاره** ثبت می‌کند
(`state = 'partial'`) — چیزی دور ریخته نمی‌شود.

**محور سؤال‌ها** (همه در جدول `iee1405.iv_bank`، نه در کد):

| # | کد | سؤال | چه چیزی به دست می‌دهد |
|---|---|---|---|
| ۱ | `activity` | «شرکت شما بیشتر در چه حوزه‌ای کار می‌کند و شما چه نقشی دارید؟» | تأیید یا اصلاح «حوزه فعالیت» فهرست |
| ۲ | `offer` | «محصول یا خدمت اصلی که امسال روی آن تمرکز دارید؟» | تطبیق با نیاز پروژه‌ها |
| ۳ | `capacity` | «بازهٔ توان فنی و ظرفیت تولید؟ (ولتاژ، تناژ، تعداد در ماه)» | عدد، نه توصیف کلی |
| ۴ | `gap` | «بزرگ‌ترین گلوگاه؟ چه چیزی وارد می‌کنید؟» | درِ ورود همکاری |
| ۵ | `coop` | «کدام همکاری جذاب‌تر است: تأمین، نمایندگی، پروژه مشترک، انتقال دانش فنی؟» | مسیر پیگیری |
| ۶ | `next` | «رابط پیگیری چه کسی است و بهترین راه تماس؟» | اقدام بعدی |
| ۷ | `evidence` | «کاتالوگ یا دیتاشیت می‌دهم؟» (پیش‌فرض پرسیده نمی‌شود) | شاهد مکتوب |
| ۸ | `reference` | «پروژه یا مشتری شاخص با اجازهٔ نام‌بردن؟» (پیش‌فرض نه) | اعتبار ادعا |

هر سؤال با یک **جملهٔ زمینه** از خودِ آینه می‌آید، تا پرسش اول تأییدی باشد نه از
صفر: «(در فهرست: «تولید» — درست است؟)»، «(در وندور لیست توانیر هستید — کدام گروه
کالا؟)»، «(غرفهٔ شما در سالن … است)». این جمله‌ها فقط از فیلدهای موجود ساخته
می‌شوند؛ چیزی از خودمان اضافه نمی‌شود.

پاسخ‌ها کجا می‌روند؟ جدول `iee1405.interviews` — **نه** `crm.organizations`:

| ستون | معنی |
|---|---|
| `company_ref` | شناسهٔ آینه، **بدون** کلید خارجی (با `DROP SCHEMA barghpa CASCADE` نمی‌شکند) |
| `company_name` | عکس نام در لحظهٔ ثبت، تا پس از بازنویسی آینه بی‌نام نماند |
| `interviewee_name` · `interviewee_role` | نام و سمت، همان دو گام اول |
| `answers` | `[{code, q, a, at}]` با زمان تهران |
| `cooperation` | جمع‌بندی از پاسخ `coop` |
| `state` | `partial` یا `done` |

بعد از ثبت، کارت همان شرکت یک سطر اضافه می‌گیرد:
«🎤 مصاحبه‌ها: ۱ مورد · آخرین: سارا موسوی (کارشناس فروش)».

تغییر سؤال‌ها **بدون استقرار مجدد**:

```sql
-- متن یک سؤال
UPDATE iee1405.iv_bank
   SET text_fa = 'ظرفیت تولید ماهانه‌تان چند دستگاه است؟'
 WHERE code = 'capacity';

-- هر هشت سؤال پرسیده شود (نه فقط شش پیش‌فرض)
UPDATE iee1405.bot_state SET value = 'true' WHERE key = 'iv_ask_all';

-- سؤال تازه به بانک
INSERT INTO iee1405.iv_bank (code, ord, topic, text_fa, ask_default)
VALUES ('price', 55, 'بازار', 'قیمت‌ها امسال نسبت به پارسال چقدر تغییر کرده است؟', true)
ON CONFLICT (code) DO UPDATE SET text_fa = EXCLUDED.text_fa;
```

### سؤال اختصاصی هر شرکت، با کمک هوش مصنوعی

بانک بالا برای همه یکی است؛ ولی هر شرکت یک یا دو نکتهٔ خاص دارد. برای همین جدول
`iee1405.iv_company_q` هست: سؤال‌های اختصاصی **پس از** سؤال‌های بانک و با کد
`custom` پرسیده می‌شوند. هیچ سؤالی خودکار ساخته نمی‌شود — هر چه در این جدول باشد
پرسیده می‌شود و هر چه نباشد، نه.

**گام ۱ — بافت شرکت را بگیرید.** یک دستور، بدون کوئری بلند:

```bash
cd ~/ZNNY-Xennic-Vault/iee1405-deploy

bash 03_ops/prompt_company.sh --list 10            # فهرست: شناسه + نام + حوزه فعالیت
bash 03_ops/prompt_company.sh "ایران ترانسفو"      # جست‌وجو با بخشی از نام
bash 03_ops/prompt_company.sh --id 12 --json       # فقط JSON (برای کپی)
bash 03_ops/prompt_company.sh --id 12 --prompt     # JSON + متن آمادهٔ درخواست به هوش مصنوعی
bash 03_ops/prompt_company.sh --questions --id 12  # سؤال‌ها همان‌طور که ربات می‌پرسد
```

خروجی `--id 12 --json` چیزی شبیه این است:

```json
{
    "id": 12,
    "name": "…",
    "flags": "tavanir_vendor",
    "halls": "38A، 38B",
    "activity": "…",
    "pilot_check": null
}
```

> [!tip] چرا اسکریپت، نه کوئری چسبانده‌شده
> کوئری چندخطی با نقطه‌دارهایی مثل `c.id` و `c.name_fa` در چت و ترمینال دو بار
> خراب شد (تبدیل به پیوند)، و روی سرورِ نسخهٔ ۰.۱.۳۹ پیام گمراه‌کنندهٔ
> `column c.activity does not exist` داد. `prompt_company.sh` هر دو را حل
> می‌کند: پیش از هر چیز می‌سنجد ستون `activity` هست یا نه و اگر نبود، می‌گوید
> «SQL نسخهٔ ۰.۱.۴۰ اعمال نشده — `bash 03_ops/deploy_sql.sh`».

اگر خواستید همان کوئری را دستی بزنید، این است (همان چیزی که اسکریپت اجرا می‌کند):

```sql
SELECT jsonb_pretty(jsonb_build_object(
         'id', c.id, 'name', c.name_fa, 'activity', c.activity,
         'halls', (SELECT string_agg(DISTINCT p.hall, '، ')
                     FROM barghpa.participation p WHERE p.company_id = c.id),
         'flags', (SELECT string_agg(f.flag, ',')
                     FROM barghpa.company_flag f WHERE f.company_id = c.id),
         'pilot_check', (SELECT pi.first_check FROM barghpa.pilot pi
                          WHERE pi.company_id = c.id)))
  FROM barghpa.company c
 WHERE c.id = 12;
```

**گام ۲ — این درخواست را به هوش مصنوعی بدهید** (همراه با خروجی گام ۱):

```
تو دستیار یک تیم فروش B2B در صنعت برق هستی. ما در نمایشگاه بین‌المللی برق
۱۶ تا ۱۹ آبان ۱۴۰۵ از این شرکت بازدید می‌کنیم و می‌خواهیم در ۲ تا ۳ دقیقه
گفت‌وگو، اطلاعاتی بگیریم که در فهرست نمایشگاه نیست.

داده‌ای که از آینه داریم (تنها منبع مجاز):
<خروجی گام ۱>

قواعد:
۱. حداکثر ۳ سؤال، هر کدام حداکثر ۲۵ کلمه، فارسی محاوره‌ای مؤدبانه.
۲. سؤال باید از دادهٔ بالا یا از صنعت برق برآید؛ هیچ عدد، نام مشتری،
   غرفه یا قراردادی نساز. اگر داده کم است، سؤال عمومی بپرس.
۳. سؤال قیمت، تخفیف، لیست مشتری و اطلاعات محرمانه نپرس.
۴. هر سؤال باید با «بله/خیر» یا یک جملهٔ کوتاه پاسخ‌پذیر باشد.
۵. خروجی را **فقط** به شکل JSON بده:
   [{"company_ref": <id>, "question": "..."}]
```

**گام ۳ — خروجی را وارد کنید** (همان JSON را داخل `jsonb_to_recordset` بچسبانید):

```sql
WITH ai AS (
  SELECT * FROM jsonb_to_recordset('[
    {"company_ref": 12, "question": "تابلوهای MV را با برند خودتان می‌سازید یا از شرکتی می‌گیرید؟"},
    {"company_ref": 12, "question": "ظرفیت ماهانهٔ تابلو در حال حاضر چند عدد است؟"}
  ]'::jsonb) AS x(company_ref bigint, question text)
)
INSERT INTO iee1405.iv_company_q (company_ref, question, source)
SELECT company_ref, question, 'ai' FROM ai
ON CONFLICT (company_ref, question) DO NOTHING;
```


```sql
-- کدام شرکت‌ها سؤال اختصاصی دارند

  FROM iee1405.iv_company_q WHERE active GROUP BY 1 ORDER BY 1;

-- سؤالی که به کار نمی‌آید، خاموش شود (پاک نمی‌شود، سابقه می‌ماند)
```

### حوزه فعالیت پس از استقرار (سه دستور)

`deploy_sql.sh` **ستون** را می‌سازد، ولی **داده** از SQLite می‌آید. اگر آینه از
یک SQLite قدیمی بارگذاری شده باشد (ساخته‌شده پیش از ۰.۱.۴۰)، ستون خالی می‌ماند و
کارت «ثبت‌نشده» نشان می‌دهد. ترتیب درست:

```bash
D=~/xennic-data/barghpa-26-iee1405
T=$D/tools

# ۱) ابزار تازه را از مخزن کپی کنید (تابع update_tools در README ابزار میدانی)
#    اگر نسخهٔ قدیمی بماند، ستون «نوع فعالیت» خوانده نمی‌شود.
git -C ~/ZNNY-Xennic-Vault fetch origin dev
grep -c activity "$T/import_barghpa.py"     # باید بزرگ‌تر از صفر باشد؛ صفر = کپی انجام نشده

# ۲) اکسل را دوباره به SQLite ببرید (یادداشت‌ها و تماس‌ها حفظ می‌شوند؛ مهاجرت ۰۰۸ خودکار اجرا می‌شود)
python3 "$T/import_barghpa.py" --src "$D/raw" --db "$D/db/barghpa_iee1405.sqlite" --dry-run
python3 "$T/import_barghpa.py" --src "$D/raw" --db "$D/db/barghpa_iee1405.sqlite" --write

# ۳) آینه را بازبارگذاری کنید (تراکنشی، با پشتیبان و selftest)
```

انتظار: در بازسازی فهرست، **۲۹۷ از ۲۹۷** شرکت حوزهٔ فعالیت دارند (اگر منبع برای
شرکتی خالی باشد، همان خالی می‌ماند — استنتاج نمی‌شود).

### هشدار سلامت چقدر پیام می‌فرستد؟

`health_watch()` حداکثر **یک هشدار در هر ۳ ساعت** می‌فرستد (قبضهٔ اتمی روی
`bot_state`). بدون این محدودیت، هر ۳۰ دقیقه یک پیام تکراری می‌آمد — ۴۸ پیام
در روز، دقیقاً وقتی روی پا ایستاده‌اید.

```bash
# برای دریافت فوری هشدار بعدی در آزمون:
SELECT iee1405.health_alert_reset();
# تغییر بازه:
SELECT * FROM iee1405.health_watch('30 minutes');
```

> [!danger] باگ رفع‌شده در ۰.۱.۱۶: خودترمیمی مرده بود
> WF-04 این‌طور نوشته شده بود: `WITH rec AS (SELECT recover_if_dead()) SELECT ...`
> اما PostgreSQL کات‌های **بدون ارجاع** را هرس می‌کند (روی ۱۶.۲ آزمودم)، پس
> `recover_if_dead()` هرگز اجرا نمی‌شد — بی‌صدا و بدون هیچ خطایی. حالا فراخوانی
> داخل `health_watch()` است و اعتبارسنجی هر کات بی‌استفاده را رد می‌کند.

### «ورودی خالی است» یا `result: []` — آیا یعنی خراب است؟

**نه، معمولاً یعنی سالم است.** وقتی `getUpdates` با `result: []` برمی‌گردد،
یعنی offset از همه پیام‌های موجود گذشته و بله چیز تازه‌ای ندارد. برای اینکه
مطمئن شوید پیامی گم نشده:

```bash
bash 03_ops/inspect_state.sh
```

خروجی سالم:

```
  offset : 8 · آپدیتهای ثبتشده : 8 · پاسخهای در صف : 0 · خطاها : 0
  ✅ همهچیز سالم است: هر آپدیتی که بله داد، ثبت و پردازش شد
```

و اگر واقعاً گم شده باشد، خودش می‌گوید:

```
  ❌ offset=8 است ولی هیچ آپدیتی ثبت نشده — پیامها از دست رفتهاند
```

در آن حالت:

```bash
bash 03_ops/replay_updates.sh --dry-run   # چند آپدیت در بله هست و چند در دیتابیس ما
bash 03_ops/replay_updates.sh             # بازخوانی از صفر
```

> [!tip] بازخوانی ایمن است
> `bot_updates` کلید یکتا روی `update_id` دارد، پس آپدیتی که قبلاً پردازش شده
> «duplicate» می‌شود و **دوباره پاسخ نمی‌گیرد**. آزمون خودکار این را تأیید
> می‌کند (دور دوم: همه duplicate، صفر پیام تازه).

### چرا آیتم خالی `{}` به گره پردازش می‌رسد

`✂️ تفکیک آپدیتها` روی `response.result` کار می‌کند. در پیمایش خالی، آرایه
تهی است و `alwaysOutputData` یک آیتم خالی عبور می‌دهد. تابع
`bot_dispatch_json('{}')` این را می‌شناسد، صفر ردیف برمی‌گرداند و **خطا
نمی‌دهد** — عمداً، وگرنه هر ۲۰ ثانیه یک خطای جعلی در سلامت می‌نشست.

> [!danger] باگ رفعشده در ۰.۱.۱۵
> صفر ردیف بودن گره پردازش باعث می‌شد n8n **همه گرههای بعدی** را رد کند؛
> یعنی پاسخ‌های ارسال‌نشده در پیمایش خالی هرگز دوباره تلاش نمی‌شدند و تضمین
> تحویل شکسته بود. حالا این گره `alwaysOutputData` دارد و اعتبارسنجی آن را
> الزامی می‌کند.

|---|---|---|
| ترتیب گره‌ها | `poll_advance()` بیشترین `update_id` را از `bot_updates` می‌خواند؛ اگر قبل از گره پردازش اجرا شود جدول خالی است و offset صفر می‌ماند | گره ثبت زمان **بعد از** پردازش اجرا می‌شود؛ اعتبارسنجی این ترتیب را الزامی می‌کند |
| آپدیت مشکل‌دار | اگر پردازش یک آپدیت شکست بخورد، همان دسته هر ۲۰ ثانیه دوباره گرفته می‌شد (طوفان) | شناسه‌های هر دسته در `poll_watch` ثبت می‌شوند؛ offset جلو می‌رود و آپدیت گم‌شده در `bot_errors` با stage=`unrecorded` می‌ماند |
| ثبت ارسال | گره ثبت ارسال `update_id` را از خروجی `sendMessage` می‌خواند که آن فیلد را ندارد → هیچ ارسالی ثبت نمی‌شد و پیام هر ۲۰ ثانیه تکرار می‌شد | `mark_sent(update_id, پاسخ بله)`؛ موفق → تحویل‌شده، ناموفق → تا ۵ تلاش و سپس رها با ثبت خطا |

> [!tip] پس از قطعی چند ساعته چه انتظاری درست است؟
> بله همه پیام‌های عقب‌افتاده را یک‌جا می‌دهد. آپدیت‌ها **همه** ثبت می‌شوند،
> اما برای `/start` و `/help` فقط **یک** راهنما در بازه ۱۰ دقیقه فرستاده می‌شود
> (وگرنه هشت پیام یکسان پشت سر هم می‌آمد). پیام‌های تأیید ثبت داده از این
> قاعده مستثنی‌اند تا دو ثبت پشت‌سرهم یک تأیید نگیرد.

### اگر گره‌ای «permission denied» داد

**رفع فوری (بدون ری‌استارت، بدون تغییر داده):**

```bash
bash 03_ops/fix_grants.sh
```

گرنت‌ها را اعمال می‌کند و بعد **واقعاً آزمایش می‌کند**: همان INSERTی که گره
«پردازش» انجام می‌دهد، با نقش `iee_app` زده می‌شود (داخل تراکنش و بازگشتی).
مجوزها فوری اثر می‌کنند؛ فقط همان گره را دوباره Execute step بزنید.

> [!warning] «دستور بدون خطا اجرا شد» کافی نیست
> فراخوانی `bot_dispatch_json` با پیام مجاز، مسیر خطا را طی نمی‌کند و به
> `bot_errors` نمی‌نویسد؛ پس می‌تواند سبز باشد در حالی که دسترسی سیکوئنس
> هنوز نیست. `fix_grants.sh` و بخش ۳.۸ تشخیص، عمداً همان INSERT را می‌زنند.



> [!danger] این خطا هیچ ربطی به n8n ندارد
> n8n با نقش `iee_app` به PostgreSQL وصل می‌شود، نه با `postgres`. هر دسترسی که
> به این نقش داده نشود، فقط در لحظه اجرا معلوم می‌شود:
>
> | پیام | معنا | رفع |
> |---|---|---|
> | `permission denied for sequence bot_errors_id_seq` | INSERT روی جدولی که شناسه‌اش `bigserial` است، بدون `USAGE` روی سیکوئنس | `GRANT USAGE, SELECT ON ALL SEQUENCES ...` |
> | `permission denied for table users` | ربات `last_seen_at` را به‌روز می‌کند اما `UPDATE` نداشت | `GRANT UPDATE (last_seen_at, bale_chat_id) ON crm.users` |
>
> هر دو در `01_sql/06_roles.sql` رفع شده‌اند. **راه‌حل دائمی:** بعد از هر تغییر
> ساختار، `bash 03_ops/deploy_sql.sh` را اجرا کنید؛ در پایان، دسترسی‌ها را
> بازبینی می‌کند و اگر کمبودی باشد نام می‌برد.

بازبینی دستی در هر زمان:

```bash
bash 03_ops/deploy_sql.sh --verify-only
# یا داخل psql:
SELECT * FROM iee1405.privilege_gaps();   -- خروجی خالی = سالم
```

> [!tip] چرا این باگ فقط روی سرور دیده شد
> آزمون‌های قبلی با کاربر `postgres` اجرا می‌شدند و همه‌چیز مجاز بود. حالا
> `test_workflow_e2e.py` کل مسیر ربات را با `SET ROLE iee_app` اجرا می‌کند،
> پس کمبود دسترسی در همان آزمون محلی قرمز می‌شود، نه در نیمه‌شب روی سرور.

### اگر گام ۴ خطای ۴۰۰ داد: «malformed request»

> [!danger] علت قطعی و رفعشده در v0.1.10
> `400 {"ok":false, "description":"Bad Request: malformed request"}` یعنی بله
> **درخواست را رد کرد**، نه اینکه شبکه مشکل داشته باشد. ریشه: گره
> `📥 دریافت پیام‌ها` بلافاصله بعد از `💓 ضربان دریافت` است و آن گره فقط `{at}`
> برمی‌گرداند؛ پس `$json.offset` وجود نداشت و عبارت به `NaN` می‌رسید →
> آدرس `?offset=NaN&limit=50&timeout=0` → رد شد.
>
> رفع: گره ضربان حالا `poll_offset() + 1 AS next_offset` را هم برمی‌گرداند و
> گره HTTP فقط `{{ $json.next_offset }}` را می‌گذارد (بدون محاسبه در n8n).

نشانه‌اش در پنل خطای گره: `ERR_BAD_REQUEST` با `status: 400` — و بخش ۳.۷
`diagnose_n8n.sh` هم دقیقاً همین را نشان می‌دهد (خط پایه ۲۰۰، شکل تولید ۴۰۰).

دو محافظ اضافه شد تا این کلاس خطا دیگر تکرار نشود:

| محافظ | چه می‌کند | اجرا |
|---|---|---|
| قاعده اعتبارسنجی | هر `$json.x` در گره HTTP باید در SQL گره بالادستی ستون داشته باشد | `python3 02_n8n/validate_workflows.py` |
| آزمون e2e | عبارت offset باید `next_offset` باشد و هیچ `Number(` نداشته باشد | `python3 03_ops/test_workflow_e2e.py` |

## ۳.۵.۴. دیدن «کدام گره گیر کرده»

هر چهار گردش‌کار با `saveExecutionProgress: true` ساخته می‌شوند؛ بنابراین n8n
داده را مرحله‌به‌مرحله ذخیره می‌کند و می‌شود دید یک اجرای **تمام‌نشده** تا کجا
رسیده است:

```bash
bash 03_ops/diagnose_n8n.sh     # بخش ۳.۲
```

خروجی، وضعیت گره‌های همان اجرا را نشان می‌دهد؛ گره‌ای که وضعیتش ثبت نشده،
همان‌جایی است که اجرا منتظر مانده.

> [!warning] سقف زمانی، گره معلق را نمی‌کشد
> هم `executionTimeout` سطح گردش‌کار و هم `EXECUTIONS_TIMEOUT` محیطی فقط
> **بین** گره‌ها بررسی می‌شوند. اگر یک گره هرگز برنگردد، این سقف هم اجرا نمی‌شود؛
> به همین دلیل هم `options.timeout` روی گره HTTP گذاشته شده و هم بخش ۳.۲
> وجود دارد.

## ۳.۵.۵. «اجراهای گیرکرده» — و چرا دیگر خطرناک نیستند

اگر گردش‌کار ۰۱ در وضعیت `running` بماند، سه لایه جلوی آسیب را می‌گیرند:

| لایه | تنظیم | کار |
|---|---|---|
| گره | `options.timeout = 20s` | درخواست معلق را می‌بندد |
| اجرا | `EXECUTIONS_TIMEOUT=45` در override | حتی اگر گره timeout را نادیده بگیرد، کل اجرا بسته می‌شود |
| داده | `💓 ضربان دریافت` پیش از درخواست | `last_poll_at` تازه می‌ماند؛ پس «شبکه قطع» از «زمان‌بند خوابیده» جدا می‌شود |

ردیف‌های مرده‌ای که از قبل مانده‌اند:

```bash
bash 03_ops/clean_executions.sh --dry-run   # فقط نمایش
bash 03_ops/clean_executions.sh             # running → crashed (هیچ ردیفی حذف نمی‌شود)
```

> [!note] چرا حذف نمی‌کنیم
> همان کاری را می‌کنیم که خودِ n8n در crash-recovery انجام می‌دهد: وضعیت به
> `crashed` تغییر می‌کند و تاریخچه می‌ماند. حذف ردیف فقط وقتی لازم است که
> واقعاً بخواهید تاریخچه اجراها را پاک کنید (و آن دستور در `diagnose_n8n.sh` نیست).

> [!important] بله خطاها را با HTTP 200 برمی‌گرداند
> پاسخ `{"ok":false,"description":"Unauthorized"}` کد ۲۰۰ دارد. بدون بازرسی،
> این «هیچ پیام تازه‌ای نیست» تلقی می‌شد. گره `🩺 بازرسی پاسخ بله` با تابع
> `poll_watch()` همین را ثبت می‌کند و در `/status` دیده می‌شود.

## ۳.۶. اگر ربات جواب نمی‌دهد — تشخیص یک‌دستوری

```bash
bash 03_ops/diagnose_n8n.sh        # فقط خواندن
```

این اسکریپت به **دیتابیس خود n8n** نگاه می‌کند (نه به خروجی CLI) و پنج چیز را می‌گوید:

| بخش | چه چیزی را نشان می‌دهد |
|---|---|
| ۱ | هر گردش‌کار: `active` و `activeVersionId` — «فعال ولی بدون نسخه منتشرشده» یعنی انتشار اثر نکرده |
| ۲ | آیا کارت `XENNIC-PG-CREDENTIAL` در `credentials_entity` هست؟ نبودنش = خطای همه گره‌های SQL |
| ۳ | آخرین اجراها و **نام گره + متن خطا** (مثلاً `password authentication failed`) |
| ۴ | `last_poll_at` / `last_error` / شمار پیام‌ها |
| ۳.۱ | خطای **رمزگشایی‌شده** آخرین اجرای ناموفق: نام گره، پیام، توضیح، کد HTTP و وضعیت هر گره |
| ۳.۲ | یک اجرای **در حال اجرا** تا کدام گره رسیده (با `saveExecutionProgress`) |
| ۳.۵ | دسترسی n8n به `$env` (یعنی `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` و وجود `BALE_API_URL`) |
| ۳.۶ | دسترسی کانتینر به `tapi.bale.ai` |
| ۳.۷ | آزمون **زنده** `getUpdates` با `node fetch`: کد، زمان پاسخ و بدنه ماسک‌شده — تفکیک «شبکه» از «n8n» |
| ۵ | گام بعدی بر اساس همان تشخیص |

> [!note] چرا `execution_data` خام نامفهوم است
> n8n داده اجرا را با قالب فشرده «flatted» ذخیره می‌کند: آرایه‌ای که عناصرش
> رشته‌های عددی اشاره‌گرند (`lastNodeExecuted: "7"` یعنی عنصر هفتم).
> `03_ops/decode_execution.py` همین را رمزگشایی می‌کند و `diagnose_n8n.sh` صدایش می‌زند.

> [!warning] ایمپورت دوباره، گردش‌کار تکراری می‌سازد مگر شناسه ثابت باشد
> فایل‌های `02_n8n/wf-*.json` از این نسخه شناسه ثابت دارند (`IEE1405-01` … `IEE1405-04`).
> بدون شناسه ثابت، هر ایمپورت یک گردش‌کار **تازه** می‌ساخت و نسخه قبلی هم فعال می‌ماند
> (دو بار `getUpdates` و پیام تکراری). `activate_all.sh` گردش‌کارهای تکراری قدیمی را
> غیرفعال می‌کند و شناسه‌ها را از خود فایل‌ها می‌خواند، نه از خروجی CLI.

> [!important] چرا «فعال» بودن در CLI کافی نیست
> سه حالت مختلف، یک نشانه دارند (ربات ساکت است و `last_poll_at` خالی):
> ۱) انتشار انجام شده ولی n8n ری‌استارت نشده؛ ۲) کارت اعتبارنامه ساخته نشده؛
> ۳) رمز `iee_app` با رمز داخل کارت یکی نیست. `diagnose_n8n.sh` این سه را از هم جدا می‌کند.

### چرا پاسخ دیر می‌رسد؟ (از نسخهٔ ۰.۱.۳۸)

زمان‌بند دریافت ۵ ثانیه است و `getUpdates` با `timeout=4` (long-poll) صدا زده
می‌شود؛ یعنی اگر پاسخ دیر می‌رسد، تقریباً همیشه سه جای دیگر است. یک دستور، جای
دقیق را می‌گوید:

```bash
bash 03_ops/latency_report.sh
```

| ستون گزارش | اگر بزرگ باشد یعنی |
|---|---|
| «بله→پایگاه» | زمان‌بند یا صف اجراهای n8n عقب است (بخش ۴ همان گزارش: مدت و فاصلهٔ اجراها) |
| «پایگاه→ارسال» | خودِ `sendMessage` بله کند است یا صف ارسال شلوغ است («در صف» بزرگ و ثابت) |
| «از آخرین دریافت (ث)» | گردش‌کار اجرا نمی‌شود یا غیرفعال شده |

دو محافظ که با بازهٔ ۵ ثانیه‌ای لازم شدند:

- **قفل ارسال (`sending_at`)**: `pending_replies(20, true)` ردیف‌ها را هنگام
  برداشتن قفل می‌کند، پس دو اجرای هم‌زمان یک پیام را دو بار نمی‌فرستند. اگر
  اجرایی در میانهٔ کار بمیرد، قفل پس از ۹۰ ثانیه خودش باز می‌شود و تلاش بعدی
  انجام می‌شود. ارسال ناموفق هم قفل را آزاد می‌کند (تلاش بعدی همان ۵ ثانیه).
- **اجرای موفق داده ذخیره نمی‌کند** (`saveDataSuccessExecution: none`): با
  بازهٔ ۵ ثانیه‌ای روزی ~۱۷ هزار اجرا داریم و ذخیرهٔ دادهٔ هر اجرا خودش n8n را
  کند می‌کرد.

### فهرست دکمه‌ای شرکت‌ها (Inline Keyboard)

دکمهٔ **🏢 لیست شرکت‌ها** (یا `/list`) فهرست ۲۹۷ شرکت نمایشگاه را صفحه‌به‌صفحه
می‌دهد: هر صفحه ۸ شرکت در **دو ستون** دکمهٔ شیشه‌ای، و ردیف آخر
«◀ صفحه قبل» و «صفحه بعد ▶». ضربه روی هر شرکت، کارتش را باز می‌کند
(با دکمهٔ «↩ بازگشت به فهرست»).

| لایه | نام | کار |
|---|---|---|
| پایگاه | `iee1405.co_page(page)` | یک صفحه: متن شماره‌دار + `inline_keyboard` دو‌ستونی + ناوبری |
| پایگاه | `iee1405.co_search(q)` | همان، روی نتیجهٔ جست‌وجو (تا ۲۴ نتیجه، ۳ صفحه) |
| پایگاه | `iee1405.co_card(id)` | کارت شرکت + دکمهٔ بازگشت |
| n8n | `💬 ارسال پاسخ` | همان `reply_markup` را می‌فرستد؛ **هیچ تغییر گردش‌کاری لازم نبود** |
| پایگاه | `bot_dispatch` | `callback_query` با دادهٔ `c:<id>` / `l:<page>` / `s:<page>` |

> [!important] هر صفحه دو مسیر دارد، عمداً
> متن هر صفحه شماره‌گذاری شده است (۱…۸). اگر بله روی نسخه‌ای
> `callback_query` را تحویل ندهد، کاربر همان کار را با **فرستادن شماره**
> یا `/list ۲` انجام می‌دهد. یک قابلیت که فقط با دکمه کار کند، در روز
> نمایشگاه ریسک است.

بررسی اینکه بله دادهٔ دکمه را واقعاً می‌فرستد (یک دکمه بزنید، بعد):

```bash
docker exec -i xennic-infra-postgres-1 psql -U n8n -d xennic -X -P pager=off \
  -c "SELECT update_id, left(raw::text, 60) AS داده FROM iee1405.bot_updates
       WHERE raw ? 'callback_query' ORDER BY update_id DESC LIMIT 3;"
```

خروجی خالی یعنی بله دادهٔ دکمه را نمی‌فرستد → مسیر شماره و `/list ۲` کار می‌کند.

**دکمهٔ «🔎 جست‌وجو»** حالا آینهٔ نمایشگاه را می‌گردد (نه CRM): یک نتیجه →
مستقیم کارت؛ چند نتیجه → فهرست دکمه‌ای. `/find` برای جست‌وجوی CRM جدا ماند.

### دکمه‌های پایین صفحه (ReplyKeyboard) و مسیر جایگزین ارسال

از نسخهٔ ۰.۱.۳۶ هر پیامی که از `pending_replies` می‌آید دکمه‌های پایین صفحه را با
خود می‌برد. زنجیره دقیقاً این است:

| لایه | نام | چه می‌کند |
|---|---|---|
| پایگاه | `iee1405.menu_keyboard()` | `{"keyboard":[["📊 امروز","🔎 جست‌وجو"],…],"resize_keyboard":true}` — برچسب‌ها همان واژه‌هایی هستند که `bot_dispatch` می‌شناسد |
| پایگاه | `iee1405.current_keyboard()` | همان، ولی با احترام به کلید `keyboard_enabled`؛ هرگز NULL نیست |
| پایگاه | `iee1405.pending_replies(n)` | ستون پنجم `reply_markup` = `COALESCE(bot_updates.reply_markup, current_keyboard())` |
| n8n | `💬 ارسال پاسخ` | `reply_markup = {{ $json.reply_markup }}` را در بدنه می‌فرستد |
| n8n | `🔀 بررسی تحویل` | اگر پاسخ بله `ok=true` نبود (یا خطا داد) به شاخهٔ جایگزین می‌رود |
| n8n | `💬 ارسال دوباره بدون دکمه` | همان پیام، بدون `reply_markup` — تا خطای دکمه هرگز پیام را نکشد |
| n8n | `✅ ثبت ارسال بدون دکمه` | `mark_sent_fallback()`: تحویل را ثبت و تکرار را می‌شمارد |

سه بار پیاپی «ارسال با دکمه رد شد ولی بدون دکمه رفت» یعنی صفحه‌کلید روی این نسخهٔ
بله پذیرفته نمی‌شود؛ خودکار خاموش می‌شود (`keyboard_enabled=false`، به‌جای دکمه
`{"remove_keyboard": true}` می‌رود) و یک ردیف در `bot_errors` ثبت می‌شود. روشن‌کردن
دوباره بدون استقرار:

```sql
UPDATE iee1405.bot_state SET value = 'true'  WHERE key = 'keyboard_enabled';
UPDATE iee1405.bot_state SET value = '0'     WHERE key = 'markup_failures';
```

> [!warning] گردش‌کار در حال اجرا با فایل مخزن یکی نیست
> اگر گره `📤 پاسخ‌های آماده ارسال` را در رابط n8n دست‌کاری کرده‌اید، همان نسخه
> اجرا می‌شود، نه فایل مخزن. پس از هر تغییر در `02_n8n/`، فایل
> `wf-01-bale-ingest.json` را دوباره ایمپورت کنید (۱۵ گره) یا پارامتر
> `reply_markup` را دستی به گرهٔ ارسال اضافه کنید.

**اصول داده (PRJ-IEE-012):** هر ادعا سطح دارد (`verified | reported | inferred | observed`).
ربات همیشه `reported` می‌نویسد — چیزی که در نمایشگاه شنیده شده، تأییدشده نیست.
هیچ خروجی هوش مصنوعی به‌عنوان واقعیت ثبت نمی‌شود.

## ۷. بازگشت (Rollback)

| چه چیزی | چگونه |
|---|---|
| گردش‌کار n8n | در رابط n8n غیرفعال کنید؛ یا `bash 03_ops/import_workflows.sh activate` روی نسخه قبلی |
| داده | `bash 03_ops/backup_now.sh` قبل از هر تغییر؛ آزمون بازگردانی با `bash 03_ops/restore_test.sh` |
| ساختار | ساختار additive است؛ برای حذف کامل فقط در محیط آزمایشی: `DROP SCHEMA iee1405 CASCADE;` — `crm` را حذف نکنید |

بازگردانی آزمایشی (هرگز مستقیم روی تولید):

```bash
docker compose -f ~/xennic-infra/docker-compose.yml exec -T postgres \
  psql -U postgres -c "CREATE DATABASE restore_test;"
docker compose -f ~/xennic-infra/docker-compose.yml exec -T postgres \
  pg_restore -U postgres -d restore_test --no-owner < ~/xennic-backups/iee-*.dump
```
