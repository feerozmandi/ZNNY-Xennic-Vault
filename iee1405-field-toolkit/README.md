### به‌روزرسانی ابزار روی سرور (بدون عوض‌کردن شاخهٔ مخزن)

`tools/` یک کپی است، نه لینک. اگر نسخهٔ قدیمی آنجا بماند، پرچم‌های تازه با
`unrecognized arguments` رد می‌شوند — دو بار همین اتفاق افتاد.

> [!warning] چرا `origin/dev` روی سرور وجود ندارد
> آن کلون با `--single-branch --branch arena/011e185b-…` ساخته شده و آن شاخه
> پس از ادغام PR #75 **حذف** شد. در چنین کلونی `remote.origin.fetch` فقط همان
> شاخهٔ مرده را نگاشت می‌کند، پس `git fetch origin dev` **تنها `FETCH_HEAD`**
> را به‌روز می‌کند و `origin/dev` ساخته نمی‌شود. نتیجه: `fatal: Not a valid
> object name origin/dev:iee1405-field-toolkit` — و در بدترین حالت، کپی
> انجام نمی‌شود ولی اسکریپت ادامه می‌دهد و آزمونِ **نسخهٔ قدیمی** سبز می‌شود.
> به همین دلیل بلوک زیر هم از `FETCH_HEAD` می‌خواند و هم پیش از کپی بررسی
> می‌کند که فهرست فایل خالی نباشد.

```bash
update_tools() {
  V=~/ZNNY-Xennic-Vault
  B=dev
  T=~/xennic-data/barghpa-26-iee1405/tools
  BK=~/xennic-data/barghpa-26-iee1405/backups/tools-$(date -u +%Y%m%dT%H%M%SZ)

  git -C "$V" fetch origin "$B" || { echo "‼️ fetch نشد — ادامه ندهید"; return 1; }

  PY=$(git -C "$V" ls-tree --name-only "FETCH_HEAD:iee1405-field-toolkit" | grep '\.py$')
  SC=$(git -C "$V" ls-tree --name-only "FETCH_HEAD:iee1405-field-toolkit/schema")
  [ -n "$PY" ] && [ -n "$SC" ] || { echo "‼️ فهرست فایل از FETCH_HEAD خوانده نشد — ادامه ندهید"; return 1; }

  mkdir -p "$BK" && cp -a "$T"/*.py "$T"/schema "$BK"/     && echo "۱) نسخهٔ قبلی در $BK"
  for f in $PY; do
    git -C "$V" show "FETCH_HEAD:iee1405-field-toolkit/$f" > "$T/$f" \
      || echo "‼️ $f"
  done
  for f in $SC; do
    git -C "$V" show "FETCH_HEAD:iee1405-field-toolkit/schema/$f" > "$T/schema/$f" \
      || echo "‼️ schema/$f"
  done

  rm -rf "$T/__pycache__"      # بایت‌کد قدیمی می‌تواند نسخهٔ قبلی را اجرا کند
  echo "۲) نشانه‌های نسخه (هر سه باید غیرصفر باشند):"
  grep -c cover-halls   "$T/pick_pilot.py"
  grep -c pilot-report  "$T/log_interaction.py"
  grep -c HALL_ORDER    "$T/build_plan.py"
  python3 "$T/test_toolkit.py" 2>&1 | tail -2       # باید «۹۵ موفق / ۰ ناموفق»
}
update_tools
```

اگر هر سه عدد صفر بودند، کپی انجام نشده — آزمون بعدی **نسخهٔ قدیمی** را
می‌سنجد و سبز شدنش دلیل درستی نیست. برای تعمیر دائمی همان کلون (اختیاری،
شاخهٔ کاری را عوض نمی‌کند):

```bash
git -C ~/ZNNY-Xennic-Vault config remote.origin.fetch '+refs/heads/dev:refs/remotes/origin/dev'
git -C ~/ZNNY-Xennic-Vault fetch origin
```

### غرفه: چه چیزی وارد می‌شود و چه چیزی نه

شیت اول («شرکت‌کنندگان») ستون غرفه **ندارد**؛ شیت دوم («فهرست کامل ۳۰۰ رکورد»)
ستون **«موقعیت غرفه»** دارد. بنابراین:

- `participation.booth_raw` = مقدار خام منبع، بدون تفسیر (همیشه).
- `participation.booth` = فقط اگر مقدار خام الگوی روشن «سالن-شماره» یا شمارهٔ
  تنها داشته باشد (مثل `38B-12`)؛ در غیر این صورت `NULL`.
- کارت میدانی: اگر `booth` باشد نشان می‌دهد، وگرنه «غرفه (خام منبع، تأییدنشده)»
  یا «غرفه ثبت نشده». هیچ‌گاه از نام شرکت یا سالن حدس زده نمی‌شود.

### ثبت بازدید سر میز

در HTML هر سالن، فرم پایین هر کارت. تعامل در حافظهٔ همان گوشی می‌ماند
(`localStorage`). پایان روز: دکمهٔ «خروجی JSON تعامل‌ها» → فایل در
`~/Downloads/`. سپس از سرور:

```bash
python3 $T/log_interaction.py --db $D/db/barghpa_iee1405.sqlite \
  --import ~/xennic-data/barghpa-26-iee1405/imports/interactions-<تاریخ>.json
```

### اقدام‌های بعدی

```bash
python3 $T/log_interaction.py --db $D/db/barghpa_iee1405.sqlite --due-list
python3 $T/log_interaction.py --db $D/db/barghpa_iee1405.sqlite --export $D/exports/interactions.csv
```

### وضعیت پایلوت: کدام‌یک از ۲۰ را واقعاً دیدید

```bash
python3 $T/log_interaction.py --db $D/db/barghpa_iee1405.sqlite --pilot-report
python3 $T/log_interaction.py --db $D/db/barghpa_iee1405.sqlite \
  --pilot-report --pilot-csv $D/exports/pilot-status.csv
```

فقط‌خواندنی است. برای هر نامزد می‌نویسد `✅ دیده شد` (با نتیجه و اقدام بعدی) یا
`— بی‌تعامل` (با سطح اطمینان تماس)، و پایان کار «مانده در سالن‌ها» را می‌شمارد:
اگر شرکت را دیدید و ثبت نکردید، همان‌جا معلوم می‌شود — نه یک هفته بعد.

هشدار مهم: «بی‌تعامل» یعنی **تعاملی ثبت نشده**، نه «شرکت نبوده». گزارش هرگز
از نبودِ رکورد نتیجه نمی‌گیرد.

## ۶. سیاست پشتیبان

- پیش از **هر** ایمپورت: `backups/barghpa_iee1405.<UTC>.pre-import.sqlite`
  با `sqlite3.Connection.backup()` — نه `cp` (کپی از پایگاه باز فایل خراب می‌دهد).
- روزانه (پیشنهاد کرون، ۷ نسخه):
  `0 2 * * * python3 ~/xennic-data/barghpa-26-iee1405/tools/backup_daily.py`
  — یا دستی با `log_interaction.py` بدون نیاز؛ جزئیات در `PRJ-IEE-015 §ابزار`.
- بازگردانی: فایل پشتیبان را روی `db/barghpa_iee1405.sqlite` کپی کنید و
  `integrity_check` بگیرید. آزمون D5.4 همین مسیر را پوشش می‌دهد.

`journal_mode=DELETE` و `synchronous=FULL` انتخاب شده‌اند چون فایل روی پوشهٔ
همگام‌شده می‌نشیند و `WAL` با همگام‌سازی فایل ناسازگار است.

| ۸ | «صفحه شرکت در برقپا» هرگز نگاشت نمی‌شد | سرستون نویسهٔ نامرئی (RTL/ZWNJ) داشت و مقایسهٔ نرمال‌شده هم برابر نمی‌شد؛ لایهٔ «مقایسهٔ بدون فاصله» اضافه شد |
| ۷ | ستون ۱۴گانه بی‌نگاشت بود | «منبع تکمیل اطلاعات»، «منابع (URL)»، «لوگو»، پنج ستون انجمن و سه ستون تأییدیهٔ توانیر نگاشت شدند (مهاجرت `004`) |

### منشأ داده: خودِ فایل می‌گوید هر رکورد از کجا آمده

شیت اصلی ستون **«منبع تکمیل اطلاعات»** و **«منابع (URL)»** دارد. بازبینی هر دو
را می‌شمارد و در پنج دسته گزارش می‌کند (سایت رسمی/شرکت، جست‌وجوی وب، منبع دیگر).
ایمپورتر `provenance_source` و `provenance_urls` را در سطح شرکت نگه می‌دارد و
`official_site` را **فقط** وقتی پر می‌کند که دامنهٔ وب‌سایت در همان منابع ذکرشده
آمده باشد — یعنی «سایت رسمی» یک ادعای قابل‌بررسی است، نه یک برچسب.

### اطمینان داده: «حدس دامنه» با «سایت رسمی» یکی نیست

بیشتر دادهٔ تکمیل‌شده با **حدس دامنه** به دست آمده (تطبیق دامنه با نام شرکت)،
نه از سایت رسمی. مهاجرت `005` این را قابل‌تصمیم می‌کند:

| مقدار `provenance_class` | معنا | اثر روی اولویت |
|---|---|---|
| `official` | منبع می‌گوید از سایت رسمی شرکت | تماس مستقیم (+۳۰) |
| `guessed` | حدس دامنه، تأییدنشده | تماس حدسی (+۱۵) |
| `portal` | فقط پورتال برق‌پا | +۱۵ اگر تماسی باشد |
| `web_search` | جست‌وجوی وب | +۳۰ |
| `unknown` | چیزی ثبت نشده | — |

هر تماس هم `contact.confidence` می‌گیرد و کارت میدانی برچسب رنگی نشان می‌دهد:
«منبع: سایت رسمی» سبز، «منبع: حدس دامنه — تأییدنشده» نارنجی. یعنی بازدیدکننده
سر میز می‌داند کدام شماره تأییدشده است و کدام حدس.

### دو ستون که فقط برای اقدام میدانی‌اند

- **`official_site`**: دامنهٔ وب‌سایت در فهرست «منابع (URL)» خودِ فایل آمده.
  این یک **شاهد** است، نه برچسب؛ با «منبع تکمیل اطلاعات» یکی نیست. ممکن است
  منبع بگوید «حدس دامنه» ولی همان دامنه در فهرست منابع باشد.
- **`google_search`**: ستون «لینک جستجوی گوگل (برای تکمیل دستی)» که برای همهٔ
  ۲۹۷ شرکت پر است. فقط ذخیره می‌شود و در کارت، **فقط برای شرکت‌های بدون هیچ
  تماس** به‌شکل پیوند «جست‌وجوی دستی (نیازمند اینترنت)» می‌آید. ابزار خودش هیچ
  درخواستی نمی‌زند؛ بازکردن پیوند تصمیم کاربر است.

سربرگ هر سالن هم خلاصهٔ پوشش را نشان می‌دهد: چند شرکت منبع «سایت رسمی»، چند
«حدس دامنه»، و چند بدون هیچ اطلاعات تماس.

### نگهبان نگاشت

به یک فیلد وصل شده باشد، بازبینی هشدار می‌دهد. همین نگهبان بود که اگر از اول

## ۷.۲. فهرست پایلوت (مرحلهٔ C)

`pick_pilot.py` فقط **نامزد پیشنهاد** می‌دهد؛ تا مالک تأیید نکند چیزی نوشته نمی‌شود.

```bash
T=~/xennic-data/barghpa-26-iee1405/tools
D=~/xennic-data/barghpa-26-iee1405

python3 $T/pick_pilot.py --n 20                      # نمایش، بدون نوشتن
python3 $T/pick_pilot.py --n 20 --csv $D/exports/pilot.csv
python3 $T/pick_pilot.py --n 20 --cover-halls --max-group 1 \
    --write --approve --approved-by "احمد فیروزمندی بندپی"      # ثبت فهرست تأییدشده
python3 $T/build_html.py --db $D/db/barghpa_iee1405.sqlite --out $D/exports/field
```

قواعد رتبه‌بندی، همه صریح و قابل بازبینی:

| عامل | امتیاز |
|---|---|
| منبع «سایت رسمی (ادعای منبع)» | +۳۰ |
| «پورتال برق‌پا» | +۱۲ |
| «جست‌وجوی وب» | +۸ |
| «حدس دامنه» | +۰ |
| وندور لیست توانیر | +۱۲ |
| دانش‌بنیان | +۸ |
| دامنه در فهرست منابع فایل | +۶ |
| اولویت مشارکت | تا +۲۰ (یک‌پنجم) |

محدودیت‌ها: شرکت بدون هیچ تماس وارد نمی‌شود (مگر `--include-empty`)، و از هر
سالن حداکثر ۴ شرکت (قابل تغییر با `--per-hall`). اگر `--write` بدون `--approve`
زده شود، ابزار با خطا متوقف می‌شود.

### دو گزینه‌ای که در v0.7 اضافه شد (واکنش به خروجی واقعی)

خروجی اولِ ۲۰ نامزد سه نقص داشت: سالن‌های **۳۸A، ۳۱A، ۳۱B هیچ نامزدی نداشتند**
(سقف `--per-hall` سقف است، نه کف)، و سه شرکتِ «ایران ترانسفو» با هم آمده بودند.

| گزینه | کار | چرا لازم شد |
|---|---|---|
| `--cover-halls` | اول از **هر سالن** یک نامزد برمی‌دارد (سالن کم‌جمعیت‌تر اول)، بعد بقیهٔ جاها با امتیاز پر می‌شود | رتبه‌بندی فقط‌امتیازی سالن کوچک را گرسنه می‌گذاشت |
| `--max-group N` | حداکثر N شرکتِ هم‌خانواده (نام با ≥۲ واژهٔ معنادار مشترک؛ واژه‌هایی که در بیش از ۸٪ نام‌های استخر تکرار شده‌اند — مثل «برق» — هویت خانواده شمرده نمی‌شوند) | سه شرکت یک گروه در سه سالن، از سقف سالن رد می‌شدند |

هر دو با هم قابل استفاده‌اند. ابزار در پایان همیشه می‌نویسد **چند سالن پوشش داده
شد** و اگر فهرست از `--n` کمتر شد، صریح می‌گوید کدام سقف مانع بوده — تا سکوت
جای گزارش را نگیرد.

```bash
python3 $T/pick_pilot.py --n 20 --cover-halls --max-group 1          # پیش‌نمایش
```

## ۷.۳. برنامهٔ روزهای بازدید — `build_plan.py`

`build_plan.py` **فقط‌خواندنی** است و از همان ۲۰ نامزد تأییدشده یک برنامهٔ A4
می‌سازد: هر روز یک صفحه، هر شرکت یک سطر، ستون «نتیجه» خالی برای دست‌نویس.

```bash
python3 $T/build_plan.py --days 4 \
    --out $D/exports/plan        # plan.html + plan.csv
```

- سالن‌ها به‌ترتیب قرارداد به **بازه‌های پیوسته** شکسته می‌شوند (برش بهینه، نه حریصانه)
  تا هر روز یک مسیر پشت‌سرهم باشد، نه چهار گوشهٔ سالن.
- ترتیب سالن‌ها در `build_plan.py` (`HALL_ORDER`) یک **قرارداد** است، نه نقشهٔ
  تأییدشده: نقشهٔ نمایشگاه دیده نشده. صفحه خودش همین را بالای برگه می‌نویسد.
- هشدارها بالای صفحه می‌آیند: خانواده‌های هم‌نام، سالن‌های بی‌نامزد، و ترکیب
  اطمینان تماس‌ها. واژه‌های عمومیِ نام (که در بیش از نیمی از نام‌ها تکرار شده‌اند)
  از هشدار خانواده حذف می‌شوند تا هشدارِ واقعی در نویز گم نشود.
- چیزی از پایگاه کم یا زیاد نمی‌شود؛ هر نامزد دقیقاً یک سطر.
- نامزدی که **فقط** برای پوشش سالن آمده (با رتبهٔ خالی هم نمی‌آمد) برچسب
  زرد «پوشش سالن» می‌گیرد؛ بقیه برچسب نمی‌گیرند. ابزار این را با اجرای دوگانهٔ
  انتخاب می‌سنجد، نه با حدس: همان انتخاب یک‌بار بدون مرحلهٔ پوشش اجرا می‌شود و
  هر که در آن فهرست هم بود، برچسب نمی‌خورد. سطر اول راهنما هم می‌گوید معنی
  برچسب چیست: «سر میز کوتاه‌تر بایستید».
- تعداد شرکت هر روز از خودِ نامزدها می‌آید، نه از حدس.

هر نامزد یک `first_check` دارد: اولین کاری که سر میز باید انجام شود —
«تأیید شماره/ایمیل با سایت رسمی»، «تأیید دادهٔ حدسی»، یا «دریافت کارت ویزیت».
پس از تأیید، `pilot.html` با همان ترتیب ساخته می‌شود.
